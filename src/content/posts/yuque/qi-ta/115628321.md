## 第 0 章 Debug

### 1.问题 1

> 我想从dev切换到main但是，dev存在一些修改，但是还没有commit，我该如何保存

#### ✅方法：使用`git stash`（推荐，用完还可以恢复）

```plain
git stash
```

这个命令会把当前工作区（**已修改但未提交**的内容）保存到 Git 的 stash 区域，并还原工作区状态（干净），然后你就可以自由切换到`main`：

```plain
git checkout main
```

💡回到`dev`后，如果你还想恢复这些修改：

```plain
git stash pop
```

idea 开发环境中，apply 选项就是保留 stash 的同时，还原 changes，也就是应用这也 changes, pop 选项就是还原 changes 但是不保留 stash

### 2.问题 2

> 如果你有一个具体场景（比如从`dev`合并第3次提交进`main`），我可以帮你写出具体的命令

#### 🎯**目标场景**：

你在`dev`分支中有很多提交，现在你想把**第 3 次提交**（不是最新提交）合并进`main`分支，不带上其他提交的变更。

---

#### 🧭解决思路：

我们要的是**只拿某次提交的内容合并进 main**，所以不能直接`git merge dev`，而是用：

✅`git cherry-pick <commit-hash>`

---

#### ✅操作步骤如下：

##### 1. 查看`dev`分支的提交历史

```plain
git checkout dev
git log --oneline
```

输出示例：

```plain
a1b2c3d (HEAD -> dev) 第5次提交
9e8f7g6 第4次提交
7h6i5j4 第3次提交   ←你想合并的提交
3k2l1m0 第2次提交
0z9x8w7 第1次提交
```

你找到**第3次提交的哈希值是**`7h6i5j4`。

---

##### 2. 回到`main`分支

```plain
git checkout main
```

---

##### 3. cherry-pick 这次提交

```plain
git cherry-pick 7h6i5j4
```

这会把该提交的变更内容复制一份，形成一条新提交记录加到`main`上。

---

#### ⛳️注意事项：

- 如果该提交依赖了前面的提交（如改了某个前面才创建的文件），可能会冲突，要解决冲突再 `git cherry-pick --continue` 。
- 如果你要合并多个提交（比如第3~5次），用：

```plain
git cherry-pick <start-commit>^..<end-commit>
# 示例
git cherry-pick 3k2l1m0^..a1b2c3d
```

If this checkbox is selected, all changes already added to the index are left intact 这个什么意思

- ChatGPT 说：

这句话的意思是：

**“如果这个复选框被选中，所有已经添加到索引（index）中的更改将保持不变。”**

---

#### 🧠解释关键词：

- **checkbox is selected** ：表示某个选项被勾选了。
- **changes already added to the index** ：指的是你已经用 `git add` 命令添加到暂存区（staging area/index）的更改。
- **left intact** ：意思是“不会被修改”或“保持原样”。

---

#### 🧩场景举例：

假设你修改了两个文件：

```plain
bash


复制编辑
modified: file1.txt   <-- 已 git add
modified: file2.txt   <-- 未 git add
```

这时候你执行某个操作（例如**Git Stash**），看到这个复选框：

✔️「If this checkbox is selected, all changes already added to the index are left intact」

👉意思是：如果你勾选这个选项，那`file1.txt`这个已添加的内容会**留在暂存区**，**不会被 stash 清除**；只会 stash`file2.txt`。

---

#### 📌换句话说：

- 勾选 ✅ ：保留 `git add` 的内容（index 不变）
- 不勾选 ❌ ：会把所有修改（包括已 add 的）一起 stash 掉，index 会被清空

### 3.问题 3

> 如果我要将某个版本的代码下载出来，或者拷贝出来，我该如何做。目前我都是push后，然后在github上点击下载。这样就可以获取到最新版本。但是我想在本地操作

### ✅方法：用`git archive`导出某个版本代码为 zip

```plain
git archive --format=zip --output=old-version.zip abc1234
```

这条命令会把`abc1234`提交时的内容打包成`old-version.zip`，你可以随意拷贝、解压。

也可以指定分支名：

```plain
git archive --format=zip --output=main-latest.zip main
```

## **<span style="color: black">第1章 Git概述</span>**

<span style="color: #333333">Git是一个免费的、开源的</span><span style="color: red">分布式版本控制系统</span><span style="color: #333333">，可以快速高效地处理从小型到大型的各种 项目。</span>

<span style="color: #333333">Git易于学习，占地面积小，性能极快。它具有廉价的本地库，方便的暂存区域和多个工作 流分支等特性。其性能优于Subversion、CVS、Perforce和ClearCase等版本控制工具。</span>

### **<span style="color: black">1.1何为版本控制</span>**

<span style="color: black">版本控制是一种记录文件内容变化，以便将来查阅特定版本修订情况的系统。</span>

<span style="color: black">版本控制其实最重要的是可以记录文件修改历史记录，从而让用户能够查看历史版本，</span>

<span style="color: black">方便版本切换。</span>

<span style="color: black">个人开发过渡到团队协作。</span>

![image.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/0fb1dc46f2a532053c8dacc89f3ad0f63e244a465989f9f90b45f0b300672ef2.png)

### 1.3**<span style="color: black">版本控制工具</span>**

#### **<span style="color: black">集中式版本控制工具</span>**

<span style="color: black">CVS、</span><span style="color: red">SVN(Subversion)</span><span style="color: black">、VSS……</span>

<span style="color: black">集中化的版本控制系统诸如CVS、SVN等，都有一个单一的集中管理的服务器，保存 所有文件的修订版本，而协同工作的人们都通过客户端连到这台服务器，取出最新的文件或 者提交更新。多年以来，这已成为版本控制系统的标准做法。</span>

<span style="color: black">这种做法带来了许多好处，每个人都可以在一定程度上看到项目中的其他人正在做些什 么。而管理员也可以轻松掌控每个开发者的权限，并且管理一个集中化的版本控制系统，要 远比在各个客户端上维护本地数据库来得轻松容易。</span>

<span style="color: black">事分两面，有好有坏。这么做显而易见的缺点是中央服务器的单点故障。如果服务器宕 机一小时，那么在这一小时内，谁都无法提交更新，也就无法协同工作。</span>

> <span style="color: black">我的理解是：我再写一段业务，我能看到其他人正在项目中写其他业务，代码在自动增加，当然每一个业务都是并发执行的。</span>

**<span style="color: black">分布式版本控制工具</span>**

<span style="color: red">Git</span><span style="color: black">、Mercurial、Bazaar、Darcs……</span>

<span style="color: black">像 Git这种分布式版本控制工具，客户端提取的不是最新版本的文件快照，而是把代码 仓库完整地镜像下来（本地库）。这样任何一处协同工作用的文件发生故障，事后都可以用 其他客户端的本地仓库进行恢复。因为每个客户端的每一次文件提取操作，实际上都是一次 对整个文件仓库的完整备份。</span>

<span style="color: black">分布式的版本控制系统出现之后,解决了集中式版本控制系统的缺陷:</span>

1.<span style="color: black">服务器断网的情况下也可以进行开发（因为版本控制是在本地进行的）</span>

2.<span style="color: black">每个客户端保存的也都是整个完整的项目（包含历史记录，更加安全）</span>

> <span style="color: black">我的理解是：我在本地写一段业务，其他人在他本地写业务，然后统一上传，如果有一段大家都修改了，那就一个人提交成功，宁另一个人修改冲突部分。</span>

### 4.1什么是分支

在版本控制过程中，同时推进多个任务，为每个任务，我们就可以创建每个任务的单独分支。使用分支意味着程序员可以把自己的工作从开发主线上分离开来，开发自己分支的时候，不会影响主线分支的运行。对于初学者而言，分支可以简单理解为副本，一个分支就是一个单独的副本。（分支底层其实也是指针的引用）

![image.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/561053592c84c19b65203697b82ca8d5c70c769d11e314e9be97ef6fe247d5cc.png)

### 4.2分支的好处

同时并行推进多个功能开发，提高开发效率。

各个分支在开发过程中，如果某一个分支开发失败，不会对其他分支有任何影响。失败的分支删除重新开始即可。

### 4.4创建分支和切换分支图解

![image.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/00fac65f94fbcdbbeeeee718eff4016a492cc371bb5e610918c0e0ff2b1132a3.png)

master、hot-fix其实都是指向具体版本记录的指针。当前所在的分支，其实是由HEAD

决定的。所以创建分支的本质就是多创建一个指针。

HEAD如果指向master，那么我们现在就在master分支上。

HEAD 如果指向 hotfix，那么我们现在就在hotfix 分支上。

所以切换分支的本质就是移动HEAD指针。

GitLab是由GitLabInc.开发，使用[MIT](https://baike.baidu.com/item/MIT%E8%AE%B8%E5%8F%AF%E8%AF%81)[许可证](https://baike.baidu.com/item/MIT%E8%AE%B8%E5%8F%AF%E8%AF%81)的基于[网络](https://baike.baidu.com/item/%E7%BD%91%E7%BB%9C)的[Git](https://baike.baidu.com/item/Git)[仓库](https://baike.baidu.com/item/%E4%BB%93%E5%BA%93)管理工具，且具有[wiki](https://baike.baidu.com/item/wiki)和issue跟踪功能。使用[Git](https://baike.baidu.com/item/Git)作为代码管理工具，并在此基础上搭建起来的web服务。GitLab由乌克兰程序员DmitriyZaporozhets和ValerySizov开发，它使用[Ruby](https://baike.baidu.com/item/Ruby%E8%AF%AD%E8%A8%80)[语言](https://baike.baidu.com/item/Ruby%E8%AF%AD%E8%A8%80)写

成。后来，一些部分用[Go](https://baike.baidu.com/item/Go%E8%AF%AD%E8%A8%80)[语言](https://baike.baidu.com/item/Go%E8%AF%AD%E8%A8%80)重写。截止2018年5月，该公司约有290名团队成员，以及2000多名开源贡献者。GitLab被IBM，Sony，JülichResearchCenter，NASA，Alibaba，Invincea，O’ReillyMedia，Leibniz-Rechenzentrum(LRZ)，CERN，SpaceX等组织使用。

### 10.3GitLab安装

#### **10.3.1 服务器准备**

准备一个系统为CentOS7以上版本的服务器，要求内存4G，磁盘50G。关闭防火墙，并且配置好主机名和IP，保证服务器可以上网。

此教程使用虚拟机：主机名：gitlab-serverIP地址：192.168.6.200

#### 10.3.2 安装包准备

Yum在线安装gitlab- ce时，需要下载几百M的安装文件，非常耗时，所以最好提前把所需RPM包下载到本地，然后使用离线rpm的方式安装。

下载地址：

> [https://packages.gitlab.com/gitlab/gitlab-](https://packages.gitlab.com/gitlab/gitlab-)ce/packages/el/7/gitlab-ce-13.10.2-ce.0.el7.x86_64.rpm

注：资料里提供了此rpm 包，直接将此包上传到服务器/opt/module 目录下即可。

#### 10.3.3 编写安装脚本
