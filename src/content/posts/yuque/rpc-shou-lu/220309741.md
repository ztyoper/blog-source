### **一、前言**

> 最近未被使用连接淘汰策略该怎么实现呢？

前面我们实现了基于SPI扩展最早连接淘汰策略、最晚连接淘汰策略、先进先出连接淘汰策略和使用次数最少连接淘汰策略，接下来，我们继续基于SPI扩展连接淘汰策略，跟上冰河的节奏，一起加油！

### **二、目标**

> 目标很明确：基于SPI扩展最近未被使用连接淘汰策略！

最近未被使用连接淘汰策略就是当服务提供者目前承载的连接数量超过配置的最大连接数时，服务提供者判断最近与服务消费者建立连接的使用的时间，目前距离当前时间最远的连接优先被淘汰。

在最近未被使用连接淘汰策略中，会基于连接的使用时间对连接列表进行排序，获取到连接列表中使用时间距离当前时间最远的连接信息，进而对获取到的连接进行淘汰处理。

本章，我们就基于SPI扩展最近未被使用的连接淘汰策略。

（8）服务消费者向服务提供者发送心跳ping消息，服务提供者响应服务消费者pong消息。服务提供者向服务消费者发送心跳ping消息，服务消费者向服务提供者响应pong消息。

（16）结果缓存通用模型中包含：结果缓存的Key和结果缓存管理器。

（17）服务提供者和服务消费者支持结果缓存。

（18）服务消费者支持基于负载均衡延迟/非延迟连接多个服务提供者（这里的多个服务提供者包括从注册中心获取到的服务提供者列表，也包括配置的服务消费者直连的多个服务提供者），或直接延迟/非延迟连接某个服务提供者，调用服务方法（重试机制）

#### **3.新增LruDisuseStrategy类**

LruDisuseStrategy类的源码详见：bhrpc-disuse-lru工程下的[io.binghe.rpc.disuse.lru.LruDisuseStrategy](http://io.binghe.rpc.disuse.lru.LruDisuseStrategy)，如下所示。

```go
@SPIClass
public class LruDisuseStrategy implements DisuseStrategy {
    private final Logger logger = LoggerFactory.getLogger(LruDisuseStrategy.class);
    private final Comparator<ConnectionInfo> lastUseTimeComparator = (o1, o2) -> {
        return o1.getLastUseTime() - o2.getLastUseTime() > 0 ? 1 : -1;
    };
    @Override
    public ConnectionInfo selectConnection(List<ConnectionInfo> connectionList) {
        logger.info("execute lru disuse strategy...");
        if (connectionList.isEmpty()) return null;
        Collections.sort(connectionList, lastUseTimeComparator);
        return connectionList.get(0);
    }
}
```

可以看到，在LruDisuseStrategy类的selectConnection()方法中，返回了connectionList列表中最近未被使用的一个元素，也就是服务提供者会断开最近未被使用的连接。

#### **4.新增配置文件**

在bhrpc-disuse-lru工程下的resources目录下的META-INF/binghe/internal目录下新增[io.binghe.rpc.disuse.api.DisuseStrategy](http://io.binghe.rpc.disuse.api.DisuseStrategy)文件，文件内容如下所示。

```go
lru=io.binghe.rpc.disuse.lru.LruDisuseStrategy
```

> 写好的功能不测试下怎么行？

#### **1.修改服务提供者**

修改bhrpc-demo-native-provider工程下的[io.binghe.rpc.demo.provider.ProviderNativeDemo#startRpcSingleServer](http://io.binghe.rpc.demo.provider.ProviderNativeDemo#startRpcSingleServer)()方法，调用RpcSingleServer类的构造方法时，将disuseStrategyType参数修改为lru，如下所示。

```go
@Test
public void startRpcSingleServer(){
    RpcSingleServer singleServer = new RpcSingleServer("127.0.0.1:27880", "127.0.0.1:27880","127.0.0.1:2181", "zookeeper", "random","io.binghe.rpc.demo", "asm", 3000, 6000, true, 30000, 16, 16, "print", 1, "lru");
    singleServer.startNettyServer();
}
```

可以看到，设置的最大连接数为1，当有两个服务消费者连接服务提供者时，就会触发最近未被使用连接淘汰策略。

运行bhrpc-demo-native-provider工程下的[io.binghe.rpc.demo.provider.ProviderNativeDemo#startRpcSingleServer](http://io.binghe.rpc.demo.provider.ProviderNativeDemo#startRpcSingleServer)()方法，输出的信息如下所示。

```go

```

可以看到，服务提供者成功连接到Zookeeper，并且启动后监听的IP地址为127.0.0.1，端口为27880。

#### **3.启动服务消费者**

运行两次及两次以上bhrpc-demo-native-consumer工程下的[io.binghe.demo.consumer.ConsumerNativeDemo#testInterfaceRpc](http://io.binghe.demo.consumer.ConsumerNativeDemo#testInterfaceRpc)()方法，也就是同时启动两个及两个以上的服务消费者。

在服务提供者日志中会找到如下日志信息。

```go

```

说明服务提供者当前连接数，大于或者等于配置的最大连接数时，就会触发最近未被使用连接淘汰策略。
