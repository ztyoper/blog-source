（7）服务消费者从注册中心获取到服务提供者发布的服务信息后，会基于SPI机制动态加载随机算法、加权随机算法、轮询算法、加权轮询算法、Hash算法和加权Hash算法的负载均衡策略，从多个服务中选择一个进行远程网络连接。

（8）服务消费者会直接与根据基于SPI机制动态加载的负载均衡策略选择出的服务提供者建立连接，实现数据交互。也就是说，后续服务消费者会与服务提供者直接实现数据交互。

#### **3.新增负载均衡实现类HashWeightServiceLoadBalancer**

HashWeightServiceLoadBalancer类位于bhrpc-loadbalancer-hash-weight工程下的[io.binghe.rpc.loadbalancer.hash.weight.HashWeightServiceLoadBalancer](http://io.binghe.rpc.loadbalancer.hash.weight.HashWeightServiceLoadBalancer)，主要的作用就是实现基于加权负载均衡的策略，源码如下所示。

```go
@SPIClass
public class HashWeightServiceLoadBalancer <T> implements ServiceLoadBalancer<T> {
    private final Logger logger = LoggerFactory.getLogger(HashWeightServiceLoadBalancer.class);
    @Override
    public T select(List<T> servers, int hashCode) {
        logger.info("基于加权Hash算法的负载均衡策略...");
        if (servers == null || servers.isEmpty()){
            return null;
        }
        hashCode = Math.abs(hashCode);
        int count = hashCode % servers.size();
        if (count <= 0){
            count = servers.size();
        }
        int index = hashCode % count;
        return servers.get(index);
    }
}
```

可以看到，在HashWeightServiceLoadBalancer类上标注了@SPIClass注解。

这里，我们实现的加权Hash算法负载均衡策略的重点是传入的hashCode值，最核心的逻辑就是获取到传入的服务提供者实例列表的前(hashCode %[servers.size](http://servers.size)())个服务提供者，从这前(hashCode %[servers.size](http://servers.size)())个服务提供者中根据hashCode选择一个。

**注意：在后续的文章中，我们会实现增强版的加权Hash算法负载均衡策略。**
