基于限流的方式来防刷，在实现上比较简单粗暴，并且也是最直接的一种实现方式，能够有效的解决针对单个接口的刷单流量问题，但是如果想要在业务流程上对这些刷单流量进行限制，也就是说，需要访问秒杀系统接口的流量按照既定的接口顺序进行访问，不得绕过某些步骤，此时，就需要引入流程编排的Token机制。

### **一、前言**

在前面实现的基于限流防刷，虽然能够解决针对单个接口的刷单流量问题，但是不能解决跳步刷单问题。也就是说，基于限流的防刷方案不能解决按照业务流程顺序调用接口的问题。此时，我们就需要引入基于Token编排机制的防刷策略。

大部分小伙伴应该对Token并不陌生，Token一般都是用来做鉴权的。在秒杀场景下，我们其实可以基于Token实现接口的编排：如果调用的接口有先后顺序，在调用下一个接口之前，要先在上一个接口获得Token令牌，带上Token令牌后才能调用下一个接口，不然就会认为是非法请求。通过这种Token编排机制，不仅可以防止大量刷单的问题，还能预防多端操作对数据的篡改问题。

### **二、本章诉求**

在流量网关层实现基于Token编排机制的防刷功能，掌握基于Token编排机制的防刷原理与实现流程，并能够将基于Token编排机制的防刷落地方案灵活应用到自身实际项目中。

### **三、Token编排的交互流程**

在秒杀系统中，我们会为获取秒杀活动列表、获取秒杀活动详情、获取秒杀商品列表、获取秒杀商品详情和抢购下单五个接口加上Token的生成和校验规则，当用户访问这些接口时，必须按照获取秒杀活动列表—&gt;获取秒杀活动详情—&gt;获取秒杀商品列表—&gt;获取秒杀商品详情—&gt;抢购下单的顺序进行访问。

为了让大家更加直观的了解Token编排的交互流程，这里，我简单画了一张时序图，如图110-1所示。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/8f91e5fb92ae9beb1740de77e2a57dc4a802f71c7d9c963c88b78470da78e3df.png)

可以看到，访问下一个接口时，会在header中带上上一个接口的header里返回的x-st-token，下一个接口会对x-st-token进行校验，如果校验成功，则执行后续业务逻辑，并返回结果。如果校验失败，则直接返回错误信息。

注意：这里每一个接口的header里返回的x-st-token都不同，下一个接口对上一个接口返回的x-st-token进行严格校验，如果校验失败，直接返回错误信息，只有校验成功，才会执行接口业务逻辑，以此达到接口编排的效果。

### **四、实现Token防刷**

本节，我们基于Token编排机制实现接口的防刷功能，主要还是在流量网关层面实现，并且客服端会配合实现。

#### **4.1 获取access-token**

access-token是用户登录后，后端程序返回的用户token认证信息，在实现token编排机制时，会以此为用户的唯一标识生成编排token，进一步实现接口的编排功能。

新建[access_token.lua](http://access_token.lua)脚本实现获取access-token的功能，[access_token.lua](http://access_token.lua)脚本的源码详见：seckill-nginx工程下的lua/[access_token.lua](http://access_token.lua)。

```go
local access_token = {}
​
function access_token.get_access_token()
    --获取请求头里的参数
    local headers = ngx.req.get_headers()
    --获取access_token
    local user_access_token = headers["access-token"]
    if not user_access_token then
        user_access_token = ""
    end
    return user_access_token
end
​
return access_token
```

并且需要将[access_token.lua](http://access_token.lua)脚本复制到OpenResty的lua目录下。

#### **4.2 获取x-st-token**

x-st-token就是用户在访问获取秒杀活动列表—&gt;获取秒杀活动详情—&gt;获取秒杀商品列表—&gt;获取秒杀商品详情—&gt;抢购下单这些接口时，通过access-token生成的编排token，客户端获取到每一个步骤的x-st-token时，会将其放到header的x-st-token中，并且调用下一个接口时，会在header中带上x-st-token。

新建[x_st_token.lua](http://x_st_token.lua)脚本，[x_st_token.lua](http://x_st_token.lua)脚本的源码详见：seckill-nginx工程下的lua/[x_st_token.lua](http://x_st_token.lua)。

```go
local x_st_token = {}
​
function x_st_token.get_token()
    --获取请求头里的参数
    local headers = ngx.req.get_headers()
    --获取access_token
    local token = headers["x-st-token"]
    if not token then
        token = ""
    end
    return token
end
​
return x_st_token
```
