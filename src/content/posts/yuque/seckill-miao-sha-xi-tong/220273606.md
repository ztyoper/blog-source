设计秒杀系统的初衷就是让用户在秒杀系统中抢购商品。所以，秒杀系统中要存在秒杀商品。对于秒杀商品来说，运营端和用户端的业务也是不同的。并且，在秒杀系统中，秒杀商品需要放到秒杀活动下。

### **一、前言**

秒杀商品从业务上来讲，也会分为C端和B端业务，C端业务主要是面向用户端抢购商品，B端业务主要是面向运营端的商品管理。用户可以通过秒杀系统查看秒杀商品，并抢购自己中意的商品。运营则可以通过秒杀商品向系统中发布商品、查看商品、对商品进行上线和下线操作。

### **二、本章诉求**

从用户端和运营端两种不同的角度充分梳理清楚秒杀商品的业务流程，了解用户和运营分别可以在秒杀商品中做哪些事情，并对秒杀商品需要提供的接口进行简单的设计。

### **三、流程设计**

用户端和运营端在秒杀系统中，都会通过秒杀活动进入秒杀商品流程，对于秒杀商品来说，用户端和运营端也会在具体流程上存在差异。也就是说，在秒杀商品的流程设计上，会分为运营端业务流程和用户端业务流程。

#### **3.1 运营端流程设计**

这里，依然可以想象一下，如果你是运营人员，你最想如何管理秒杀商品呢？接下来，就站在运营人员的角度来简单梳理下，秒杀商品需要为运营提供的功能。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/e7b6b41b2afe31b73c6fabb2ac24525b587706bb4a2877cd28ab4646a7db9567.png)

对于运营端来说，精简业务后，当运营人员登录秒杀系统，可以通过秒杀活动来发布秒杀商品，查看秒杀商品的列表，在秒杀商品页面可以对秒杀商品进行上线和下线操作。当秒杀商品设置为下线状态时，运营人员则只能查看当前被下线的秒杀商品，不能再对下线的秒杀商品进行操作。

#### **3.2 用户端流程设计**

相对于运营端，用户端的秒杀商品业务流程就比较简单了，用户在登录系统后，可以通过秒杀活动进入秒杀商品页面，在秒杀商品页面对商品进行抢购。用户抢购商品时，会有一个限制，就是只有在商品状态为上线状态，并且当前时间在商品秒杀时间周期内才能对商品进行抢购。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/94586cb5c98facf940c8d7b7a590cb93eddcba6ccb2aa06bde95734683eb6674.png)

### **四、接口设计**

从运营端和用户端梳理完业务流程后，大概就知道在秒杀系统中，针对秒杀商品要提供哪些功能了，进而结合数据模型，就能够大概推测出秒杀商品要提供哪些接口，以及接口的参数和响应数据大概是什么样子了。

#### **4.1 总体接口设计**

对于秒杀商品来说，业务精简后总体上需要提供的接口有：保存秒杀商品、获取秒杀商品列表、获取秒杀商品详情、更新秒杀商品状态。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/c4b595afa65142e94e30309b99a2f2516b46d596b4a5549f7a24b91a6811bc7c.png)

其中，运营人员可以使用所有的接口对秒杀商品进行全面的管理。对于用户来说，则只能访问获取秒杀商品列表和获取秒杀商品详情的接口，不能访问保存秒杀商品和更新秒杀商品状态的接口。

#### **4.2 保存秒杀商品**

保存秒杀商品的接口链接可以设计成类似http://{ip:port}/goods/saveSeckillGoods的形式，其中，{ip:port}可以根据实际情况进行替换。

接口参数类似如下所示。

```go
{
    "goodsName": 商品名称,
    "activityId": 活动id,
    "originalPrice": 商品原价,
    "activityPrice": 商品秒杀价,
    "initialStock": 参与秒杀的商品初始库存,
    "limitNum": 限购个数,
    "description": 商品描述
}
```

返回的结果数据类似如下所示。

```go
{
    "code":状态码,
    "data":提示信息
}
```

#### **4.3 获取秒杀商品列表**

获取秒杀商品列表的接口链接可以设计成类似http://{ip:port}/goods/getSeckillGoodsByActivityId的形式，其中，{ip:port}可以根据实际情况进行替换。

接口参数类似如下所示。

```go
{
    "activityId": 秒杀活动id
}
```

返回的结果数据类似如下所示。

```go
{
    "code":状态码,
    "data":[
              {
                  "id": 秒杀商品id,
                  "goodsName": 秒杀商品名称,
                  "activityId": 秒杀活动id,
                  "startTime": 秒杀开始时间,
                  "endTime": 秒杀结束时间,
                  "originalPrice": 商品原价,
                  "activityPrice": 商品秒杀价,
                  "initialStock": 参与秒杀的商品初始库存,
                  "availableStock": 参与秒杀的商品当前库存,
                  "limitNum": 限购个数,
                  "description": 秒杀商品描述,
                  "imgUrl": 秒杀商品图片,
                  "status": 秒杀商品状态
              }
           ]
}
```

更新秒杀商品状态的接口链接可以设计成类似http://{ip:port}/goods/updateStatus的形式，其中，{ip:port}可以根据实际情况进行替换。


### **五、总结**

本章，主要从运营端和用户端分别梳理了秒杀商品的业务流程，其中，运营端主要是对秒杀商品进行全面的管理，而用户端则只能查看秒杀商品的信息。对于秒杀系统中的秒杀商品来说，业务精简后需要提供的接口包括：保存秒杀商品、获取秒杀商品列表、获取秒杀商品详情、更新秒杀商品状态，并对这些接口简单的设计了接口的链接格式和数据交互格式。
