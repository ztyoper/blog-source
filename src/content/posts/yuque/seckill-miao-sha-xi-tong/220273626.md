秒杀系统为用户抢购商品提供了平台，用户可以在秒杀系统中抢购自己心仪的商品，最终对自己心仪的商品下单购买。而运营端则可以根据活动查看当场秒杀活动下所产生的订单数据。

### **一、前言**

在秒杀系统中，对精简后的秒杀订单业务，也会分成用户端和运营端两种不同的业务。相比于秒杀活动和秒杀商品来说，秒杀订单业务恰好与其相反，秒杀活动和秒杀商品的业务在运营端稍微复杂些，而秒杀订单业务则在用户端稍微复杂些。

### **二、本章诉求**

从用户端和运营端两种不同的角度充分梳理清楚秒杀订单的业务流程，了解用户和运营分别可以在秒杀订单中做哪些事情，并对秒杀订单需要提供的接口进行简单的设计。

### **三、流程设计**

用户端和运营端在秒杀系统中，多多少少都会涉及到秒杀订单的业务，不过对于秒杀订单来说，用户端的业务会比运营端的业务略显复杂些。后续对于用户查看商品、抢购、下单等流程是重点优化的地方，这里，先从业务流程上设计和实现秒杀系统的订单业务流程。

#### **3.1 用户端流程设计**

对于用户来说，从商品页面抢购商品后，会跳转到抢购下单的页面，填写购买的数量后进行下单，如果一切正常则会成功提交订单。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/197e29aef03bd659d243e69684f9e5fec52cb398235147a6a09cb26066446d8f.png)

对于用户端来说，秒杀订单业务精简后，当用户登录秒杀系统，可以通过秒杀活动查看秒杀商品，在秒杀商品页面对商品发起抢购下单，在下单时，系统会检验限购个数和商品库存，检验通过后，则会成功提交订单。

**注意：这里初步只会对商品维度的限购个数和商品库存进行校验，后续还会对用户维度的限购、秒杀资格等信息进行校验。**

#### **3.2 运营端流程设计**

运营端在秒杀订单业务中，比用户端要简单些，运营人员登录系统后，可以通过秒杀活动查看当前活动下所产生的订单信息。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/5a5319ba619de999269f7f48d33735d5c3882ef9b40430b1d6ff5df7e9f2c8d9.png)

对于运营端来说，秒杀订单业务精简后，当运营人员登录秒杀系统，可以通过秒杀活动查看当前活动下所产生的秒杀订单信息，方便后续运营人员根据订单核对当前秒杀活动的收益。

### **四、接口设计**

从用户端和运营端梳理完业务流程后，大概就知道在秒杀系统中，针对秒杀订单要提供哪些功能了，进而结合数据模型，就能够大概推测出秒杀订单要提供哪些接口，以及接口的参数和响应数据大概是什么样子了。

#### **4.1 总体接口设计**

对于秒杀订单来说，业务精简后总体上需要提供的接口有：保存秒杀订单、获取用户维度的订单列表和获取活动维度的订单列表。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/0d42edfa0db346d945b14e72219a4e9229069fdba2e40253491fc9ec34eeb7aa.png)

对于用户端业务来说，可以调用保存秒杀订单的接口进行下单，并能够获取用户维度的订单列表来查看订单数据。对于运营端业务来说，可以获取活动维度的订单列表来查看订单数据。

#### **4.2 保存秒杀订单**

保存秒杀订单的接口链接可以设计成类似http://{ip:port}/order/saveSeckillOrder的形式，其中，{ip:port}可以根据实际情况进行替换。

接口参数类似如下所示。

```go
{
    "userId": 用户id,
    "goodsId": 商品id,
    "activityId": 活动id,
    "quantity": 购买数量
}
```

返回的结果数据类似如下所示。

```go
{
    "code":状态码,
    "data":提示信息
}
```

#### **4.3 获取用户维度的订单列表**

获取用户维度的订单列表的接口链接可以设计成类似http://{ip:port}/order/getSeckillOrderByUserId的形式，其中，{ip:port}可以根据实际情况进行替换。

接口参数类似如下所示。

```go
{
    "userId":用户id
}
```

返回的结果数据类似如下所示。

```go
{
    "code": 状态码,
    "data":[
             {
                "id": 订单id,
                 "userId": 用户id,
                 "goodsId": 商品id,
                 "goodsName": 商品名称,
                 "activityPrice": 秒杀价格,
                 "quantity": 购买数量,
                 "orderPrice": 订单总金额,
                 "activityId": 活动id,
                 "status": 订单状态,
                 "createTime": 创建时间
             }
           ]
}
```

#### **4.4 获取活动维度的订单列表**

获取活动维度的订单列表的接口链接可以设计成类似http://{ip:port}/order/getSeckillOrderByActivityId的形式，其中，{ip:port}可以根据实际情况进行替换。

接口参数类似如下所示。

```go
{
    "activityId": 秒杀活动id
}
```

返回的结果数据类似如下所示。

```go
{
    "code": 状态码,
    "data":[
             {
                "id": 订单id,
                 "userId": 用户id,
                 "goodsId": 商品id,
                 "goodsName": 商品名称,
                 "activityPrice": 秒杀价格,
                 "quantity": 购买数量,
                 "orderPrice": 订单总金额,
                 "activityId": 活动id,
                 "status": 订单状态,
                 "createTime": 创建时间
             }
           ]
}
```

### **五、总结**

本章，主要从用户端和运营端分别梳理了秒杀订单的业务流程，其中，用户端可以对商品进行抢购下单，并按照用户维度查看订单列表。运营端则可以根据秒杀活动维度查看订单列表。对于秒杀系统中的秒杀订单业务来说，业务精简后需要提供的接口有：保存秒杀订单、获取用户维度的订单列表和获取活动维度的订单列表，并对这些接口简单的设计了接口的链接格式和数据交互格式。
