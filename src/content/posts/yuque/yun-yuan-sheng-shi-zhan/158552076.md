## 2、Namespace

> 名称空间用来隔离资源

![tmpDC9E.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/8c1c12754908967d57b81bbd591c0167c747259e328df8492a0a87ccf34a36dc.png)

> 应用A这样就不会访问到配置`A-dev`

### 1、命令行方式

```bash
kubectl get ns # 获取所有的名称空间
kubectl create ns hello # ns === namespace
kubectl delete ns hello # 默认的名称空间像；default 这些是不能被删除的
```

### 2、Yaml方式

```yaml
apiVersion: v1
kind: Namespace # 名称空间类型。之前貌似就是这样配置pod资源的。现在这样来配置名称空间
metadata:
  name: hello # 名字是hello
```

```yaml
kubectl apply -f hello.yaml #即可创建名称空间
kubectl delete -f hello.yaml # 删除时，推荐这种写法。这样可以删除hello.yaml配置文件配置的所有资源。删的干净一点
```

## 3、Pod

> 运行中的`一组`容器，Pod是kubernetes中应用的最小单位.

![tmpDC5B.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/a83ff5c0f0c87d6d2594686bb228250db0b31da4da1fcf70cb0dfe45c104e2ad.png)

> File Puller是一个容器。负责下载文件。
> Web Server是一个项目容器。负责搜索Volume中的文件并发送出去。
> 这样该pod就构成一个具有一种完整功能的`最小单元`。

### 1、命令行方式

```bash

# 跟docker启动容器类似。该pod会默认运行在default名称空间中。
# 根据调度者选择一个可以运行该pod的机器进行运行。
kubectl run mynginx --image=nginx 

# 查看default名称空间的Pod
kubectl get pod 
# 查看指定名称空间的Pod
kubectl get pod -n 名称空间的名字


# 描述default名称空间的Pod
kubectl describe pod 你自己的Pod名字
# 描述指定名称空间的Pod
kubectl describe pod 你自己的Pod名字 -n 名称空间的名字


# 删除默认名称空间下的pod 
kubectl delete pod Pod名字
# 删除指定名称空间下的pod 
kubectl delete pod Pod名字 -n 名称空间的名字


# 查看default名称空间的Pod的运行日志 没有加"pod"是因为只有"pod"才有日志
#如果一个pod有多个容器。那么查询logs就是 Pod名字 容器名字
kubectl logs Pod名字
# 阻塞式查看日志
kubectl logs -f Pod名字 
# 查看指定名称空间的Pod的运行日志
kubectl logs Pod名字 -n 名称空间的名字


# 每个Pod - k8s都会分配一个ip 。 比直接get，能多获取IP信息，部署在哪一个节点上
kubectl get pod -owide
# 使用Pod的ip+pod里面运行容器的端口
curl 192.168.169.136 # 默认是该IP对应的Pod中的第一个容器的端口号。所以不写也没有问题
# 集群中的任意一个机器以及任意的应用都能通过Pod分配的ip来访问这个Pod

watch -n 2 kubectl get pods -A # 每隔2秒执行一次
kubectl get pods -A -w # 可以一直观察状态变化打印的日志。
```

## 5、Deployment

> 控制Pod，使Pod拥有多副本，自愈，扩缩容等能力

### 1、自我修复

```yaml
# 清除所有Pod，比较下面两个命令有何不同效果？会惧怕kubectl delete 。删除后就不会修复了。
kubectl run mynginx --image=nginx

# 使用这种方式进行部署pod。将不会惧怕kubectl delete 。 拥有自愈（重启）能力
# 部署的pod的名称为mytomcat-长串id。而该pod的标签被设置为了mytomcat。后面Service处有用
kubectl create deployment mytomcat --image=tomcat:8.5.68

kubectl get deploy # 查询到部署的mytomcat
kubectl delete deploy mytomcat # 才能真正删除pod.和pod的部署
```

```bash
kubectl create deployment my-dep --image=nginx --replicas=3
```

### 4、自愈&故障转移

- 停机
- 删除Pod
- 容器崩溃
- ....

`其实就是自我修复`

> 自愈：pod出现问题可以重启。更新周期是5分钟
> 故障转移：机器停电后。可以将pod转移到其他机器上。更新周期是5分钟。因为平时也可能会因为网络原因。下线个30~60s

### 5、滚动更新

> 不停机更新：
> 我部署了一个nginx。并且有3个副本。现在我要部署新版本nginx。每次Running了一个新版本的nginx容器,就将老版本的一个nginx容器下线。这样就做到了不停机更新。

```bash
kubectl set image deployment/my-dep nginx=nginx:1.16.1 --record # --record会在版本历史中保存这句命令。而不是简单的<none>
#您可以实时监控滚动更新过程，查看新的 Pod 是否已经成功创建并且旧的 Pod 是否已经被替换。
#如果输出显示 deployment "my-dep" successfully rolled out，则表示滚动更新已经完成。
kubectl rollout status deployment/my-dep
```

> kubectl set image deployment/&lt;资源名称&gt; &lt;容器名称&gt;=&lt;新镜像名称&gt; 这样就可以将部署的资源的`所有副本`替换为新版本的了。

```yaml
kubectl edit deployment/my-dep  # 返回yaml结果，查看容器名称。
kubectl get deployment/my-dep -oyaml # 返回yaml结果，查看容器名称。 
#两种查看容器名称的方法。deploy === deployement 可以相互替换
```

### 6、版本回退

```bash
#历史记录
kubectl rollout history deployment/my-dep


#查看某个历史详情
kubectl rollout history deployment/my-dep --revision=2

#回滚(回到上次)
kubectl rollout undo deployment/my-dep

#回滚(回到指定版本)
kubectl rollout undo deployment/my-dep --to-revision=2
```

## 5、Service

> <span style="color: rgb(34, 34, 34)">将一组pods公开为网络服务的抽象方法。</span>
> <span style="color: rgb(34, 34, 34)">比如是sky-take-out 部署后设置副本为3个。这3个pods的label都是sky-take-out。这就是一组pods</span>
> <span style="color: rgb(34, 34, 34)">Service就是来实现负载均衡的。</span>

```bash
#暴露Deploy
kubectl expose deployment sky-take-out --port=8000 --target-port=80

#查看哪些Pod的label是sky-take-out
kubectl get pod -l app=sky-take-out # -l = label但这里只能是-l ， 替换为-label会报错

#查看default名称空间中的所有pod的标签
kubectl get pod --show-labels
```

```yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    app: sky-take-out
  name: sky-take-out
spec:
  selector:
    app: sky-take-out
  ports:
  - port: 8000
    protocol: TCP
    targetPort: 80
```

### 1、ClusterIP

> ClusterIP：只有`集群中`才可以使用`Service提供的IP+暴露的端口`或者`Service提供的域名+暴露的端口`进行`负载均衡`和服务发现。

```bash
# 等同于没有--type的。默认--type就是ClusterIP类型的
# sky-take-out 就是绑定label为sky-take-out的所有pods的80端口
# label为sky-take-out 是在 kubectl create deployment sky-take-out --replicas=3是设置为sky-take-out的
kubectl expose deployment sky-take-out --port=8000 --target-port=80 --type=ClusterIP

# 查看映射结果
kubectl get service # 或者写svc也行

这样的好处就是：集群中访问生成的10.96.228.50:8000 或者 sky-take-out.default.svc:8000去负载均衡地将请求分配给这一组label是
sky-take-out的pods。这样就不用记住三个label是sky-take-out的pod对应的IP：172.31.x.x了。
其实ClusterIP用的少。一般使用NodePort，NodePort可以来让外网能访问到。后面会讲。
集群的pod就在一个网段中，pod互相可以通信。这里说明一下:三台虚拟机本来是192.168.x.x的IP，但是访问集群中的pod时是
使用生成的三个172.31.x.x的IP地址来访问pod的。

sky-take-out.default.svc是集群中生成的域名，只能在集群中使用。域名是啥？ www.baidu.com这就是域名
```

```yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    app: sky-take-out
  name: sky-take-out
spec:
  ports:
  - port: 8000
    protocol: TCP
    targetPort: 80
  selector: # 选择label是啥的pod进行。负载均衡
    app: sky-take-out
  type: ClusterIP
```

### 2、NodePort

> 集群外也可以访问。

```bash
kubectl expose deployment sky-take-out --port=8000 --target-port=80 --type=NodePort
```

```yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    app: sky-take-out
  name: sky-take-out
spec:
  ports:
  - port: 8000
    protocol: TCP
    targetPort: 80
  selector:
    app: sky-take-out
  type: NodePort
```

> NodePort范围在 30000-32767 之间
> ![image.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/273221586c7eff2ed5f7238f60dc57d82b85fd35b20458056a6f6d007b1d26d3.png)
> 1. 本质就是将（所有 `label` 为 `sky-take-out` 的 `pods` 生成一个负载均衡端口） `10.96.13.9:8000` 映射到 `虚拟机公网IP+32393` 。192.168.127.131是虚拟机的局域网IP。可以使用cpolar来生成临时公网IP。
> 2. 这个时候。访问 `虚拟机公网IP+32393` 就不是将请求进行 `随机` 负载均衡。而是换浏览器发送 `请求` ， `请求` 才会被分配给不同的pod。
> 3. 这时三个虚拟机都建立了32393端口的映射！！！
> `192.168.127.131:32393``192.168.127.130:32393``192.168.127.129:32393`都可以接受请求。

#### 2、路径重写

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress  
metadata:
  annotations: 
    nginx.ingress.kubernetes.io/rewrite-target: /$2
  name: ingress-host-bar #ingress的名称
spec:
  ingressClassName: nginx
  rules:
  - host: "hello.atguigu.com"
    http:
      paths:
      - pathType: Prefix
        path: "/"
        backend:
          service:
            name: hello-server
            port:
              number: 8000
  - host: "demo.atguigu.com"
    http:
      paths:
      - pathType: Prefix
        path: "/nginx(/|$)(.*)"  # 正则表达式
        backend:
          service:
            name: nginx-demo  ## java，比如使用路径重写，去掉前缀nginx
            port:
              number: 8000
```

## 7、存储抽象

![tmp2884.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/fb6b35369695e6a5a55f123ab5086c07ed04db178bb5d4931991e6a92a9221ee.png)

1. 假如黑色的Pod在 `node03` 上挂掉，5min后又在 `node02` 上拉起。这时重新创建的 `/tmp` 映射文件是空的。如果pod是mysql。这是肯定不行的。所以像 `docker -v` 那样文件映射（挂载）是不行的。而且映射的文件太多，每个节点上都有数量不等的若干映射文件也不好管理。
2. 因此我们在 `node01` 上设置一个 `/nfs/data` 的文件管理目录。所有映射的文件都在目录里面。而且每一个节点又有对应挂载这个文件目录的 `/bak/data` 目录。即使 `node01` 上的 `pod` 挂掉在其他节点上拉起后。也可以通过 `/nfs/data` 挂载到 `/bak/data` 的文件目录来进行数据访问。
3. 上述我们选择使用的是 `nfs` （网络文件系统）的框架。 `NFS` 是一种基于TCP/IP传输文件系统协议。通过使用NFS协议，客户机可以像访问本地目录 一样访问远程服务器中的共享资源。
4. 记住：nfs是共享存储，不是复制到其他节点。
5. Glusterfs NFS CephFS 都是网络文件系统

### 1、PV&PVC

> 原生方式数据挂载存在以下缺点：
> 1. 要事先创建挂载的文件目录。如 `/nfs/data/nginx-pv` 目录。
> 2. 删除pod后。创建的挂载的文件目录 `/nfs/data/nginx-pv` 里面的文件 `仍然存在` 。
> 3. 无法指定挂载的文件目录 `/nfs/data/nginx-pv` 的存储空间上限。

> *PV:持久卷(Persistent Volume),将应用需要持久化的数据保存到指定位置。也就是*`/nfs/data/nginx-pv`*挂载的路径。真实存储文件的地方。*
> *PVC：持久卷申明（Persistent Volume Claim），申明需要使用的持久卷规格。相当于申请书。*
> *解决了缺点2，3*

![tmpFDB3.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/37031d922366f1bd1261a0cbbf6604e38b9180e92cfba53382055d2f242046dc.png)

1. 使用静态供应的方式。动态供应的方式在kubesphere中讲。
2. 我们首先要创建PV。PV的路径是指定了的。
3. 然后创建申请书PVC。申请书PVC和PV之间的绑定是在创建PVC时创建的。 `storageClassName: nfs`
4. 然后在部署pod的时候引用申请书PVC

> 静态供应
