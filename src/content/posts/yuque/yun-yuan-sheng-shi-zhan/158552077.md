# Kubernetes基础概念

## 1、是什么

![image.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/513013f7f62a334b55f08ea158ff4d50391a36f591f38c779219cdc7d0501c75.png)

1. 传统部署：一个App内存泄露，就会导致内存用完，将其他App挤下线。
2. 虚拟化部署：虚拟机太过笨重。
3. 容器化部署：使用容器的镜像就可以了。比如：redis的linux的容器镜像就携带了所需依赖和配置文件以及一个小型linux系统（大部分系统配置（几十个G）是使用宿主机的）。因此容器的大小也就比直接在宿主机上下载一个redis大一点。但极大地提高了移植性。

> 一旦多个项目启动，几十个这些项目所需的容器：redis , mysql ....启动在多个服务器上。将难以管理容器。如果一个项目所需的容器炸了。我们急需启动另一个新的。在使用docker run 容器管理5个以内的容器还好说。但现在我们急需一个大规模容器编排系统：K8S
> 1. 编：一个 `项目` 所需的各个 `容器` 可能会分配在多个 `服务器` 中。我们需要对其编号。
> 2. 排：编好的不同 `项目` 旗下的 `容器` 之后才好进行 `排列组合` 。

kubernetes具有以下特性：

- **服务发现和负载均衡** Kubernetes 可以使用 DNS 名称或自己的 IP 地址公开容器，如果进入容器的流量很大， Kubernetes 可以负载均衡并分配网络流量，从而使部署稳定。

1. 负载均衡：一个项目（苍穹外卖后端服务器）容器，部署到多个机器上。我们这样是为了应对高并发。而k8s可以将传过来的请求进行自动的分配给不同机器上的项目容器。这样就可以高并发访问。做到负载均衡了。和nginx有点像。
2. 服务发现：一个项目（苍穹外卖后端服务器）容器炸掉后。请求不会发给这个挂掉的容器。

- **存储编排** Kubernetes 允许你自动挂载你选择的存储系统，例如本地存储、公共云提供商等。

1. 存储编排：没有之前，一个下线的容器在机器上开辟的硬盘空间还留在哪。造成硬盘垃圾碎片。k8s存储编排后，下线的容器用到的硬盘空间会被回收掉。一个新上线的容器所需硬盘空间会像k8s请求。k8s掌握一个大片的硬盘空间的管理和分发回收。数据库的空间会不会被回收还不知道。

- **自动部署和回滚** 你可以使用 Kubernetes 描述已部署容器的所需状态，它可以以受控的速率将实际状态 更改为期望状态。例如，你可以自动化 Kubernetes 来为你的部署创建新容器， 删除现有容器并将它们的所有资源用于新容器。

1. 自动部署不太清楚。
2. 回滚：假设京东商城6.1版本部署在三台机器上。国庆来临。又部署了京东商城10.1版本覆盖之前那三台机器上的容器。结果有bug。k8s可以管理快速回滚到6.1版本。

- **自动完成装箱计算** Kubernetes 允许你指定每个容器所需 CPU 和内存（RAM）。 当容器指定了资源请求时，Kubernetes 可以做出更好的决策来管理容器的资源。

1. 每一个容器又被一个类似 `沙地` 的东西包裹起来。监控者容器的所有信息。如cpu，memory的使用情况。而且可以限制内存的使用情况。超过限制就让容器强制下线。这个设置就叫装箱。

- **自我修复** Kubernetes 重新启动失败的容器、替换容器、杀死不响应用户定义的 运行状况检查的容器，并且在准备好服务之前不将其通告给客户端。

1. 自我修复：挂掉的容器，甚至挂掉的是只启动了一个的项目容器。都可以在其他机器或本机器上秽土转生。

- **密钥与配置管理** Kubernetes 允许你存储和管理敏感信息，例如密码、OAuth 令牌和 ssh 密钥。 你可以在不重建容器镜像的情况下部署和更新密钥和应用程序配置，也无需在堆栈配置中暴露密钥。

1. 类似springcloud的管理中心。集中管理密钥。

***<span style="color: #2F54EB">Kubernetes 为你提供了一个可弹性运行分布式系统的框架。 Kubernetes 会满足你的扩展要求、故障转移、部署模式等。 例如，Kubernetes 可以轻松管理系统的 Canary 【金丝雀】部署。</span>***

## 2、架构

### 1、工作方式

Kubernetes**<span style="color: #F5222D">Cluster =</span>**N**<span style="color: #F5222D">Master</span>**Node**<span style="color: #F5222D">+</span>**N**<span style="color: #F5222D">Worker</span>**Node：N主节点+N工作节点； N&gt;=1

N个领导人不是`同一时间`有多个领导人。而是在唯一领导人`失联`后。其他节点可以投票选出新的领导人。这种又称之为`高可用`。而这个唯一领导人是Master Node 中的Leader Node 。

![image.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/ecbbb984add7779f36333c0a9a3ba76d6d2da4f3e0d6ed11ba75be8bca1b9960.png)

#### 1、控制平面组件（Control Plane Components）

控制平面的组件对集群做出全局决策(比如调度)，以及检测和响应集群事件（例如，当不满足部署的`replicas`字段时，启动新的[pod](https://kubernetes.io/docs/concepts/workloads/pods/pod-overview/)）。

控制平面组件可以在集群中的任何节点上运行。 然而，为了简单起见，设置脚本通常会在同一个计算机上启动所有控制平面组件， 并且不会在此计算机上运行用户容器。 请参阅使用 kubeadm 构建高可用性集群中关于多 VM 控制平面设置的示例。

##### kube-apiserver

API 服务器是 Kubernetes[控制面](https://kubernetes.io/zh/docs/reference/glossary/?all=true#term-control-plane)的组件， 该组件公开了 Kubernetes API。 API 服务器是 Kubernetes 控制面的前端。

Kubernetes API 服务器的主要实现是[kube-apiserver](https://kubernetes.io/zh/docs/reference/command-line-tools-reference/kube-apiserver/)。 kube-apiserver 设计上考虑了水平伸缩，也就是说，它可通过部署多个实例进行伸缩。 你可以运行 kube-apiserver 的多个实例，并在这些实例之间平衡流量。

##### etcd

etcd 是兼具一致性和高可用性的键值数据库，可以作为保存 Kubernetes 所有集群数据的后台数据库。

您的 Kubernetes 集群的 etcd 数据库通常需要有个备份计划。

要了解 etcd 更深层次的信息，请参考[etcd 文档](https://etcd.io/docs/)。

##### kube-scheduler

控制平面组件，负责监视新创建的、未指定运行[节点（node）](https://kubernetes.io/zh/docs/concepts/architecture/nodes/)的[Pods](https://kubernetes.io/docs/concepts/workloads/pods/pod-overview/)，选择节点让 Pod 在上面运行。

调度决策考虑的因素包括单个 Pod 和 Pod 集合的资源需求、硬件/软件/策略约束、亲和性和反亲和性规范、数据位置、工作负载间的干扰和最后时限。

##### kube-controller-manager

在主节点上运行[控制器](https://kubernetes.io/zh/docs/concepts/architecture/controller/)的组件。

从逻辑上讲，每个[控制器](https://kubernetes.io/zh/docs/concepts/architecture/controller/)都是一个单独的进程， 但是为了降低复杂性，它们都被编译到同一个可执行文件，并在一个进程中运行。

这些控制器包括:

- 节点控制器（Node Controller）: 负责在节点出现故障时进行通知和响应
- 任务控制器（Job controller）: 监测代表一次性任务的 Job 对象，然后创建 Pods 来运行这些任务直至完成
- 端点控制器（Endpoints Controller）: 填充端点(Endpoints)对象(即加入 Service 与 Pod)
- 服务帐户和令牌控制器（Service Account & Token Controllers）: 为新的命名空间创建默认帐户和 API 访问令牌

##### cloud-controller-manager

<span style="color: #222222">云控制器管理器是指嵌入特定云的控制逻辑的</span>[控制平面](https://kubernetes.io/zh/docs/reference/glossary/?all=true#term-control-plane)<span style="color: #222222">组件。 云控制器管理器允许您链接集群到云提供商的应用编程接口中， 并把和该云平台交互的组件与只和您的集群交互的组件分离开。</span>

`cloud-controller-manager`仅运行特定于云平台的控制回路。 如果你在自己的环境中运行 Kubernetes，或者在本地计算机中运行学习环境， 所部署的环境中不需要云控制器管理器。

与`kube-controller-manager`类似，`cloud-controller-manager`将若干逻辑上独立的 控制回路组合到同一个可执行文件中，供你以同一进程的方式运行。 你可以对其执行水平扩容（运行不止一个副本）以提升性能或者增强容错能力。

下面的控制器都包含对云平台驱动的依赖：

- 节点控制器（Node Controller）: 用于在节点终止响应后检查云提供商以确定节点是否已被删除
- 路由控制器（Route Controller）: 用于在底层云基础架构中设置路由
- 服务控制器（Service Controller）: 用于创建、更新和删除云提供商负载均衡器

#### 2、Node 组件

节点组件在每个节点上运行，维护运行的 Pod 并提供 Kubernetes 运行环境。

##### kubelet

一个在集群中每个[节点（node）](https://kubernetes.io/zh/docs/concepts/architecture/nodes/)上运行的代理。 它保证[容器（containers）](https://kubernetes.io/zh/docs/concepts/overview/what-is-kubernetes/#why-containers)都 运行在[Pod](https://kubernetes.io/docs/concepts/workloads/pods/pod-overview/)中。

kubelet 接收一组通过各类机制提供给它的 PodSpecs，确保这些 PodSpecs 中描述的容器处于运行状态且健康。 kubelet 不会管理不是由 Kubernetes 创建的容器。

##### kube-proxy

[kube-proxy](https://kubernetes.io/zh/docs/reference/command-line-tools-reference/kube-proxy/)是集群中每个节点上运行的网络代理， 实现 Kubernetes[服务（Service）](https://kubernetes.io/zh/docs/concepts/services-networking/service/)概念的一部分。

kube-proxy 维护节点上的网络规则。这些网络规则允许从集群内部或外部的网络会话与 Pod 进行网络通信。

如果操作系统提供了数据包过滤层并可用的话，kube-proxy 会通过它来实现网络规则。否则， kube-proxy 仅转发流量本身。

### 2.2、自己组建架构理解

![tmpEC46.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/c38a05b8cc65da16326c6936e87608001214e2cd65f4317395b06d7f8701dade.png)

1. 整个硅谷集团就是一个Kubernetes cluster(集群)
2. 东厂、西厂、南厂都是Work Node

1. 每个厂有个厂长（kubelet）用来监控该机器中的容器的状态。及时像秘书部通信（api）

3. 一个硅谷总部就是一个Master Node
4. 资料库（etcd）存储决策者的决策信息。配置资料等。
5. 调度者（sched）调度项目该启动到哪一个Work Node上
6. 门卫大爷（k-proxy）知道想要访问的容器的请求地址。而且每一个机器上的门卫大爷消息是互通的。都知道自己和其他机器上容器的请求端口。
7. 云-决策部（外联部）是上云项目时需要和其他集团进行交互的一个部门。

> 下面是模拟项目容器启动：
> 1. kubectl命令行：程序员输入：kubectl create deploy 飞机项目(myapp) --image=nginx （暂时不太明白nginx的意思）
> 2. 决策者作为程序员的傀儡开始发送号令给 `api-server` 。我们要启动一个飞机项目。
> 3. `api-server` 给调度者 `(scheduler)` 发送请求，调度者说这个飞机项目大。西厂存储大。就在西厂启动吧。
> 4. `api-server` 就向 `etcd` 中保存决策信息。然后将飞机项目发给西厂。
> 5. 运行一段时间后，西厂的飞机项目挂掉了。 `kubelet` 及时给 `api-server` 说。
> 6. `api-server` 询问决策者是取消掉飞机项目还是重启。
> 7. 决策者说重启。 `api-server` 又给调度者 `(scheduler)` 发送请求。调度者说东厂和西厂重启。
> 8. `api-server` 又将该决策存储在 `etcd` 中。并通知东厂启动飞机项目和西厂重启飞机项目。
> 9. 如果在东厂的汽车项目想要访问飞机项目。就问自己机器的门卫大爷（k-proxy）飞机项目的请求端口在哪。门卫大爷说我们厂有一个飞机项目的端口。西厂有一个飞机项目的端口。
> 10. 然后我就去顺利地去访问我想访问的端口。

### 1、创建过程概述

![tmp217C.png](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/d7779cb0483638074d9fd3a82e869bc58d18cc210e33381dd418335ec29f35ba.png)

1. 每台机器先装 `Docker` 容器化环境。
2. 每台机器再装 `kubelet` 厂长。
3. 每台机器装 `kubectl` + `kubeadm`

1. `kubectl` : 方便程序员写指令。当然这个 `kubectl` 在 `Master Node` 中才有用。 `Work Node` 中的kubectl后期可以删除。
2. `kubeadm` ：方便程序员快速部署 `k8s` 集群。部署完成后可以删除。

4. 向你想要作为 `Master Node` 的机器的 `kubeadm` 中输入 `kubeadm init` 。这样， `kubelet` 会帮你下载 `Master Node` 所需的5个组件。
5. 向你想要作为 `Work Node` 的机器的 `kubeadm` 中输入 `kubeadm join` 。这样， `kubelet` 会帮你下载 `k-proxy` 组件。

### 2、使用kubeadm引导集群

#### 1、下载各个机器需要的镜像

```java
#在安装kubelet-1.20.9 kubeadm-1.20.9 kubectl-1.20.9之后。可以提前下载相关组件的镜像。防止使用kubeadm下载下述镜像出现卡顿失败问题。
#上述三个不是容器运行。因此不需要下载对应的镜像。
#下述的镜像Master Node 和 Work Node都可以下载。只是多余不用罢了。
#下载好镜像后。kubeadm设置好Master Node后。之后kubelet就控制镜像是否容器化运行。
sudo tee ./images.sh <<-'EOF'
#!/bin/bash
images=(
kube-apiserver:v1.20.9
kube-proxy:v1.20.9
kube-controller-manager:v1.20.9
kube-scheduler:v1.20.9
coredns:1.7.0
etcd:3.4.13-0
pause:3.2
)
for imageName in ${images[@]} ; do
docker pull registry.cn-hangzhou.aliyuncs.com/lfy_k8s_images/$imageName
# registry.cn-hangzhou.aliyuncs.com/library
done
EOF
   
chmod +x ./images.sh && ./images.sh #给予下载权限。让其自行下载
```

#### 2、初始化主节点

```bash
#所有机器都添加master域名映射，让所有机器都知道Master Node的域名是谁，以下需要修改为自己的
echo "192.168.127.131  cluster-endpoint" >> /etc/hosts 
#使用ping cluster-endpoint 成功说明上条命令执行成功。

#主节点初始化。kubeadm只在主节点运行
kubeadm init \
--apiserver-advertise-address=192.168.127.131 \ # Master Node的IP
```
