# 任务调度debug

> 教训：不应该在存储文件的时候将服务器的 ip 地址拼接进去。之后无法修改。

> 任务调度为什么使用项目进行统一管理：1.任务之间具有关联性，而非直接的独立。实施阶段的任务，验收阶段的任务。
> 2.更清晰的管理层级，如果以单独任务进行派发，后期任务列表会非常多。

> 依赖管理：对于 dubbo ,我们在多模块项目当中，时常出现一个 controller 的 业务 service 层 需要调用 其他 模块的 service 层。如 GroupController 的 GroupService ,因此 使用 dubbo, 进行调用（解除了 添加 依赖 GroupService,但是 需要添加依赖 Dubbo, 因此我认为 Dubbo 不应该 存在 重要的 子依赖）。问题来了 Dubbo 需要调用一些 Common 中的 pojo 类？？？带补充》》
> 补充来了，我发现 controller 的 业务 service 层 需要调用 其他 模块的 service 层， 添加略微不同的业务方法的话，会出现很多 代码复制，也不好处理 dubbo 依赖， （解除了 添加 依赖 GroupService,但是 需要添加依赖 Dubbo, 解除一个又添加一个很是无奈）。直接在 controller 中 添加 接口，然后将 需要调用的 GroupService 进行 dubbo， 添加，因为一般单体多模块架构，都会在 pmhub-admin 这个地方 添加过 dubbo 依赖，这样就不用处理 dubbo 依赖了。并且重要的是： 没有大段 代码复制了。
> 事实证明，貌似 dubbo 在单体多模块项目中可以解决 循环依赖的问题。

> 1. 在数据库设计中，通常 **从属于另一张表的实体（从表）存外键** ，而 **主要表（主表）不存外键** 。
> 需求： 项目 绑定一个 群组，群组绑定 一个 项目。需要在项目中点击群组按钮，跳转按钮。如果设置了 属性 groupId ，会导致 上述 为了避免代码复制 而只修改 接口 controller 层的操作会出现问题：无法进行 project.setGroupId 的操作，除非再次进行调用 projectService 的修改业务。并且一般主表不存储 外键。因此操作如下：
> 点击 群组按钮后 ，查询 group 表，选中目标 projectId 对应的 群组。在群组中 点击 项目按钮，就直接是 跳转项目了。这样就实现了双向跳转。

> 放弃使用 dubbo 远程调用 zty-im-platform 等服务，因为单体多模块，可以通过添加本地模块依赖方式进行方法调用，并不需要使用 nacos 配合 dubbo 进行远程调用。多微服务时，才需要远程调用。| 比喻 | Feign 像是“浏览器发送请求”，Dubbo 像是“内网打电话” |
> OpenFeign：你就像一个浏览器，请求一个 REST 接口，发一个 HTTP 请求，收到 JSON 响应。
> Dubbo：你像一个内网电话，通过 TCP，打通一条快速的数据管道，传输的是压缩过的二进制数据。

### 22.Q22

✅你看到的现象：

Maven 在`package`打包时：

1. **即使本地仓库已有 jar/pom 文件** ，它仍然 **先访问远程仓库（如 Nexus）**
2. 然后才使用本地依赖
3. 某些模块明明本地有，但还是报错或延迟

---

📦为什么 Maven 会「先访问远程」再「用本地」？

这是**Maven 的核心依赖解析机制**所决定的，尤其当你使用的是`-SNAPSHOT`**版本**：

🔁对于 SNAPSHOT 依赖，Maven 的默认行为：

| 类型 | 默认行为 |
| --- | --- |
| `RELEASE` | **只下载一次**，本地存在就用本地 |
| `SNAPSHOT` | **每次构建都尝试检查远程仓库是否有更新**（除非禁用快照更新） |

🧠Maven 的逻辑是：

“SNAPSHOT 可能是开发中的版本，可能随时有变化，所以我需要**每次构建时检查远程仓库**中的最新元数据（maven-metadata.xml）”

即使你本地已经有了完整的`.jar`和`.pom`，它也会尝试访问：

```plain
ruby


复制编辑
http://localhost:8081/repository/maven-public/com/laigeoffer/pmhub/zty-im-friend/0.0.1-SNAPSHOT/maven-metadata.xml
```

---

✅怎么避免这种行为？

✅方法 1：关闭 SNAPSHOT 的远程更新（推荐）

修改你的`settings.xml`，在`<profiles>`中添加：

```plain
xml


复制编辑
<profiles>
  <profile>
    <id>no-snapshot-update</id>
    <repositories>
      <repository>
        <id>central</id>
        <url>http://localhost:8081/repository/maven-public/</url>
        <snapshots>
          <enabled>true</enabled>
          <updatePolicy>never</updatePolicy>
        </snapshots>
        <releases>
          <enabled>true</enabled>
        </releases>
      </repository>
    </repositories>
  </profile>
</profiles>

<activeProfiles>
  <activeProfile>no-snapshot-update</activeProfile>
</activeProfiles>
```

这样可以禁止 SNAPSHOT 检查远程更新，**只用本地**。

---

✅方法 2：使用离线模式（只用本地依赖）

打包时加上`-o`（offline）参数：

```plain
bash


复制编辑
mvn clean package -o
```

这会完全跳过远程仓库，只使用本地缓存。

---

✅方法 3：把依赖版本固定为 RELEASE

如果你只是临时测试，也可以不使用`0.0.1-SNAPSHOT`，而使用：

```plain
xml


复制编辑
<version>0.0.1</version>
```

这样 Maven 就不会去找`maven-metadata.xml`。

---

🚫当前问题的总结：

你的`zty-im-friend`,`zty-im-user`,`zty-im-group`等模块是`SNAPSHOT`版本，Maven 默认**每次构建都检查远程仓库中的 maven-metadata.xml 是否有更新**，即使本地有也会这样做。

---

✅建议做法（最佳实践）：

1. 在你开发/调试阶段，为避免 Nexus 拉失败， **使用** `-o` **离线构建** 。
2. 或配置 `updatePolicy=never` ，不去更新 SNAPSHOT。
3. 确保 `.lastUpdated` 不残留。
4. 本地模块，建议用 `mvn install` 安装到本地仓库，而不是依赖远程。
5. 最终部署版本，用 `RELEASE` 避免快照引发的问题。

### 23.Q23

✅正确的含义和注释写法如下：

```plain
xml


复制编辑
<repositories>
    <repository>
        <id>nexus-public</id>
        <url>http://localhost:8081/repository/maven-public/</url>

        <!-- 配置从此仓库下载正式版本依赖（非-SNAPSHOT） -->
        <releases>
            <enabled>true</enabled> <!-- 启用对 release 版本的解析 -->
            <updatePolicy>always</updatePolicy> <!-- 每次构建都检查是否有更新 -->
        </releases>

        <!-- 配置从此仓库下载快照版本依赖（SNAPSHOT） -->
        <snapshots>
            <enabled>true</enabled> <!-- 启用对 snapshot 版本的解析 -->
            <updatePolicy>always</updatePolicy> <!-- 每次构建都检查是否有更新 -->
        </snapshots>
    </repository>
</repositories>
```

---

🔍各配置项含义：

| 配置项 | 含义 |
| --- | --- |
| `enabled` | 是否启用该仓库对该版本类型（release/snapshot）的支持 |

---

🔍`updatePolicy=always`的真正行为是：

**每次构建时，Maven 都会强制检查远程仓库中的该依赖（POM/metadata）是否有更新，哪怕本地已经存在该依赖文件。**

---

✅对比三种常用值：

| `updatePolicy` | 行为说明 |
| --- | --- |
| `always` | 每次构建都访问远程仓库，看依赖是否更新，即使本地已有也会去检查。适用于 SNAPSHOT 等常变化的依赖。 |
| `daily`*(默认)* | 每天最多只检查一次。第一次会访问远程，之后的一天内用本地缓存。适用于 release 依赖。 |
| `never` | 永远不检查远程仓库，只用本地已有版本。如果没有，构建会失败。 |

---

⚠️重要说明：

- Maven 先查本地仓库，如果发现本地的 `.lastUpdated` 文件存在（即上次尝试从远程拉取失败），那么 **会跳过本地，直接去远程尝试重新获取** 。
- 即使本地存在 jar，如果设置了 `always` ，也还是会 **访问远程元数据文件（如** `maven-metadata.xml` **）进行版本比较** 。

---

你本地已有`zty-im-friend-0.0.1-SNAPSHOT.jar`，如果仓库设置了：

```plain
xml


复制编辑
<updatePolicy>always</updatePolicy>
```

```plain
ruby


复制编辑
http://localhost:8081/repository/maven-public/com/laigeoffer/pmhub/zty-im-friend/0.0.1-SNAPSHOT/maven-metadata.xml
```

来看看是否有新的 SNAPSHOT。如果失败，它会报错**即使本地有 jar 文件**，因为它不能确定是不是最新的。

---

✅最终建议：

如果你在开发环境中频繁改动 snapshot 依赖，建议保留`always`。但如果网络或私服不稳定、且你确定版本固定，也可以临时设为：

```plain
xml


复制编辑
<updatePolicy>never</updatePolicy>
```

这样 Maven 会优先使用本地已有依赖，跳过远程检查，避免构建失败。
