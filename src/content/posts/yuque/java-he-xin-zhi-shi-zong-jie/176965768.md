1. **工具及插件规范**

- 统一采用Axure作为产品设计的工具
- Web端设计组件统一引用Element_compment_2.1

- Mobile端应用暂不统一引用组件库，产品设计参照公司移动端前端实现规范进行设计；具体规范文件公司svn获取；

1. **设计成果的组织**

1. **设计文件组织的组织原则**

根据项目功能规模多少来决定设计文件的组织形式，具体组织原则如下：

- 项目功能模块清晰可控（功能模块数量&lt;10）,通常设计文件采用1个axure文件交付设计成果。设计文件命名规则:项目名_日期；例如：

胜利工程铁军云校_20190422.rp

- 项目功能模块多，而且耦合度低，通过一个设计文件交付会导致设计文件过大，不便于查看时，建议每个模块独立一个设计文件。设计文件命名规则：项目名_模块名_日期；

例如：华润医药EHS风险管理信息化项目_岗位责任制_20190422.rp

1. **设计内容的组织原则**

- 产品设计的axure成果必须包含版本记录，按照更新记录表的要求进行填写更新内容；

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/206455e022ad8ee4847ef6597384980c99cb44043829d66ff60752fc0d085ded.png)

- 每个功能模块建立独立的文件夹、出现多个版本时也通过文件加进行组织区分（多个版本的文件夹命名建议采用统一的日期格式命名），应用场景为web端的功能模块设计文件直接命名为：web端，应用场景为mobile端的功能模块设计文件直接命名为mobile端，每个设计文件包含该模块完整的功能交互及跳转。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/24e81f3baba8ffb58dfa9025313dea92520036b2e97d8329ddf1c1d99700f779.png)

- 通用的交互设计单独建立一个文件夹，设计文件的命名按照：web/mobile-功能名来命名，例如:web-组织机构选择。

1. **数据库设计规范**

统一数据库表、字段、索引等命名规范，提高数据库的可读性，系统的稳定性和可维护性。

#### 2.5.1数据库表字段命名规范

<span style="color: #494949">每个数据库表中，建表时必须包含以下字段：</span>

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| id | varchar | 主键 |
| del_flag | Integer | 删除标识：0=未删除；1=已删除 |
| create_time | date | 创建时间 |
| created_by | varchar | 创建人ID |
| updated_time | date | 更新时间 |
| updated_by | varchar | 修改人ID |
| by_office_id | varchar | 所属组织id |

针对以上字段框架会定义基础类，建议每一个Entity继承该基础类

#### 2.5.2建表规则

1. 【强制】表达是与否概念的字段，必须使用is_xxx的方式命名，数据类型是unsignedtinyint（1表示是，0表示否），此规则同样适用于大数据平台建表。 说明：任何字段如果为非负数，必须是unsigned。

2. 【强制】表名、字段名必须使用小写字母或数字；禁止出现数字开头，禁止两个下划线中间只出现数字。数据库字段名的修改代价很大，因为无法进行预发布，所以字段名称需要慎重考虑。

正例：getter_admin，task_config，level3_name

反例：GetterAdmin，taskConfig，level_3_name

3. 【强制】表名不使用复数名词。

说明：表名应该仅仅表示表里面的实体内容，不应该表示实体数量，对应于持久化类名也是单数形式，符合表达习惯。

4. 【强制】禁用保留字，如desc、range、match、delayed等，参考数据库官方保留字。

5. 【强制】唯一索引名为uk_字段名；普通索引名则为idx_字段名。

说明：uk_即unique key；idx_即index的简称。

6. 【强制】小数类型为decimal，禁止使用float和double。

说明：float和double在存储的时候，存在精度损失的问题，很可能在值的比较时，得到不正确的结果。如果存储的数据范围超过decimal的范围，建议将数据拆成整数和小数分开存储，或者字符串方式存储。

7. 【强制】如果存储的字符串长度几乎相等，使用CHAR定长字符串类型。

8. 【强制】varchar是可变长字符串，不预先分配存储空间，长度不要超过5000，如果存储长度大于此值，定义字段类型为TEXT，独立出来一张表，用主键来对应，避免影响其它字段索引效率。

9. 【强制】表必备三字段：id, create_time, update_time。

说明：其中id必为主键，类型为 vchar、单表时自增、步长为1；或者自定义自增序列；分表时确保分表之间的全局唯一。create_time, update_time的类型均为date_time类型。

10【强制】 字符集使用utf8mb4 ，排序规则使用utf8mb4_general_ci

11.【推荐】表的命名最好是加上“分类_业务名称_表的作用”，避免与其它业务表关联时有混淆。

分类为一下几点

系统表 sys 开头

关联表 link 开头

业务表 tran开头

基本数据表ms开头

正例：tran_tiger_task /tran_tiger_reader / ms_mpp_config

12.【推荐】库名与应用名称尽量一致。

13.【推荐】如果修改字段含义或对字段表示的状态追加时，需要及时更新字段注释。

14.【推荐】字段允许适当冗余，以提高性能，但是必须考虑数据同步的情况。冗余字段应遵循：

1）不是频繁修改的字段。

2）不是varchar超长字段，更不能是text字段。

正例：航班号经常在各个业务系统中使用到，避免查询时需要调用航班表服务获取。

15.【推荐】单表行数超过500万行或者单表容量超过2GB，才推荐进行分库分表。

说明：如果预计三年后的数据量根本达不到这个级别，请不要在创建表时就分库分表。

反例：某业务三年总数据量才2万行，却分成1024张表，问：你为什么这么设计？答：分1024张表，不是标配吗？

16.【参考】合适的字符存储长度，不但节约数据库表空间、节约索引存储，更重要的是提升检索 速度。

正例：人的年龄用unsignedtinyint（表示范围0-255，人的寿命不会超过255岁）；海龟就必须是smallint，但如果是太阳的年龄，就必须是int；如果是所有恒星的年龄都加起来，那么就必须使用bigint。

#### 2.5.3 索引

1. 【强制】业务上具有唯一特性的字段，即使是组合字段，也必须建成唯一索引。

说明：不要以为唯一索引影响了insert速度，这个速度损耗可以忽略，但提高查找速度是明显的；另外，即使在应用层做了非常完善的校验和控制，只要没有唯一索引，根据墨菲定律，必然有脏数据产生。

2. 【强制】超过三个表禁止join。需要join的字段，数据类型保持绝对一致；多表关联查询时，保证被关联的字段需要有索引。

说明：即使双表join也要注意表索引、SQL性能。

3. 【强制】在varchar字段上建立索引时，必须指定索引长度，没必要对全字段建立索引，根据实际文本区分度决定索引长度。

说明：索引的长度与区分度是一对矛盾体，一般对字符串类型数据，长度为20的索引，区分度会高达90%以上，可以使用count(distinct left(列名,索引长度))/count(*)的区分度来确定。

4. 【强制】页面搜索严禁左模糊或者全模糊，如果需要请走搜索引擎来解决。

说明：索引文件具有B-Tree的最左前缀匹配特性，如果左边的值未确定，那么无法使用此索引。

5. 【推荐】如果有orderby的场景，请注意利用索引的有序性。orderby最后的字段是组合索引的一部分，并且放在索引组合顺序的最后，避免出现file_sort的情况，影响查询性能。

正例：where a=? and b=? order by c;索引：a_b_c

反例：索引中有范围查找，那么索引有序性无法利用，如：WHERE b&gt;10ORDER BY a;索引无法排序。

6. 【推荐】利用覆盖索引来进行查询操作，来避免回表操作。

说明：如果一本书需要知道第11章是什么标题，会翻开第11章对应的那一页吗？目录浏览一

下就好，这个目录就是起到覆盖索引的作用。

正例：IDB能够建立索引的种类：主键索引、唯一索引、普通索引，而覆盖索引是一种查询的

一种效果，用explain的结果，extra列会出现：using index.

7. 【推荐】利用延迟关联或者子查询优化超多分页场景。

说明：MySQL并不是跳过offset行，而是取offset+N行，然后返回放弃前offset行，返回N

行，那当offset特别大的时候，效率就非常的低下，要么控制返回的总页数，要么对超过特

定阈值的页数进行SQL改写。

正例：先快速定位需要获取的id段，然后再关联：

SELECT a.* FROM表1a,(selectidfrom表1 where条件LIMIT 100000,20 ) b where a.id=b.id

8. 【推荐】SQL性能优化的目标：至少要达到range级别，要求是ref级别，如果可以是consts

最好。

说明：

1）consts单表中最多只有一个匹配行（主键或者唯一索引），在优化阶段即可读取到数据。

2）ref指的是使用普通的索引。（normal index）

3）range对索引进范围检索。

反例：explain表的结果，type=index，索引物理文件全扫描，速度非常慢，这个index级别

比较range还低，与全表扫描是小巫见大巫。

9. 【推荐】建组合索引的时候，区分度最高的在最左边。

正例：如果wherea=?andb=?，a列的几乎接近于唯一值，那么只需要单建idx_a索引即可。

说明：存在非等号和等号混合判断条件时，在建索引时，请把等号条件的列前置。如：wherea&gt;?

and b=? 那么即使a的区分度更高，也必须把b放在索引的最前列。

10.【参考】创建索引时避免有如下极端误解：

1）误认为一个查询就需要建一个索引。

2）误认为索引会消耗空间、严重拖慢更新和新增速度。

3）误认为唯一索引一律需要在应用层通过“先查后插”方式解决。

#### 2.5.4 SQL规则

1. 【强制】单表查询一律使用mybatis-plus进行查询

2. 【强制】 在代码中写分页查询逻辑时，若count 为0 应直接返回，避免执行后面的分页语句。

3. 【强制】不得使用外键与级联，一切外键概念必须在应用层解决。

说明：（概念解释）学生表中的student_id是主键，那么成绩表中的student_id 则为外键。

如果更新学生表中的student_id，同时触发成绩表中的student_id更新，则为级联更新。

外键与级联更新适用于单机低并发，不适合分布式、高并发集群；级联更新是强阻塞，存在数据库更新风暴的风险；外键影响数据库的插入速度

4. 【强制】禁止使用存储过程，存储过程难以调试和扩展，更没有移植性。

5. 【强制】数据订正时，删除和修改记录时，要先select，避免出现误删除，确认无误才能执行更新语句。

7. 【强制】数据订正时，删除和修改记录时，要先select，避免出现误删除，确认无误才能执行更新语句。

##### 分支命名规则

分支命名由六组组成，如下所示：**主版本号.子版本号.修订版本号.编译版本号。**

- 主版本号：由数字组成。跨版本不保证兼容性，规则强制要求遵守。
- 子版本号：由数字组成。相同主版本号内保持兼容，规则强制要求遵守。
- 修订版本号，最长六位数字。编译规则取决于使用工具，规则强制要求遵守。
- 编译版本号， 最长六位数字，如果是发布合并至master，则tag使用编译流水；如果是hotfix或者release分支，默认为0，规则强制要求遵守。

master 分支：master 为主分支，也是用于部署生产环境的分支，确保master分支稳定性。master 分支一般由release以及hotfix分支合并，任何时间都不能直接修改代码。

develop 分支：develop 为开发分支，始终保持最新完成以及bug修复后的代码。一般开发的新功能时，feature分支都是基于develop分支下创建的。

feature 分支：开发新功能时，以develop为基础创建feature分支。分支命名: feature- 开头的为特性分支，命名规则: feature-user_module、 feature-cart_module。

release分支：release 为预上线分支，发布提测阶段，以release-*分支代码为基准提测。命名规则遵循release-*，*为版本号，版本号规则参加章节4.6，必须强制要求遵守命名规则。

hotfix 分支：线上出现紧急问题时，需要及时修复，以master分支为基线，创建hotfix分支，修复完成后，需要合并到master分支和develop分支。分支命名: hotfix-*开头的为修复分支，版本号定义为当前master最新的tag号为基准，最后将编译版本号置为0，如当前master的最新tag为1.6.1.123456，则对应的hotfix的版本号为1.6.1.0。

**总结：当有一组feature开发完成，首先会合并到develop分支，进入提测时，会创建release分支。如果测试过程中若存在bug需要修复，则直接由开发者在release分支修复并提交。当测试完成之后，合并release分支到master和develop分支，此时master为最新代码，用作上线。**

##### 分支详解

- 主分支master

Git主分支的名字，默认叫做master。它是自动建立的。代码库应该有一个、且仅有一个主分支。master分支用来定义发布版本，所有发布过生产环境的版本都在master上以tag标示。如下所示：

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/03ee82a849b105e49d7415fe7c3d36d170cc90a6263d293ec48094d65ba87c8f.png)

- master分支生产发布了三次，则创建了三个tag，分别为：tag 1.6.0.11、tag 1.6.1.12、tag 1.7.0.13。
- 开发分支develop
- 日常开发应该在另一条分支上完成。我们把开发用的分支，定义为develop。
- ![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/d2b7eb9f7d101d759f2e989e033393d7990dacd3f0ac2a111ed2ba93373fe01c.png)
- 这个分支可以用来生成代码的最新隔夜版本（nightly）。如果想正式对外发布，需要从develop分支创建release-*分支进行稳定的测试。Git创建Develop分支的命令：
- git checkout -b develop master
- 临时性分支
- 前面讲到版本库的两条主要分支：master和develop。前者用于正式发布，后者用于日常开发。其实，常设分支只需要这两条就够了，不需要其他了。但是，除了常设分支以外，还有一些临时性分支，用于应对一些特定目的的版本开发。临时性分支主要有三种：功能（feature）分支、预发布（release）分支、修补bug（hotfix）分支。
- ![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/9dde5f92df7f71713e76aa19ea85108eb32df63165604b552502b79fabe136d0.png)
- 这三种分支都属于临时性需要，使用完以后，应该删除，使得代码库的常设分支始终只有master和develop。
- 1）功能分支(feature)
- 它是为了开发某种特定功能，从develop分支上面分出来的。开发完成后，要再并入develop。该分支命名规则参考章节1.3.4.4，采用feature-*的形式命名，其中feature-x中的x为功能的名称，如feature-user_module。flow如下所示：
- ![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/9dde5f92df7f71713e76aa19ea85108eb32df63165604b552502b79fabe136d0.png)
- 创建一个功能分支，如下所示：
- git checkout -b feature-x develop
- 开发完成后，将功能分支合并到develop分支：
- git checkout develop
- git merge --no-ff feature-x
- 删除feature分支：
- git branch -d feature-x
- 注意：使用--no-ff参数后，会执行正常合并，在Master分支上生成一个新节点。为了保证版本演进的清晰，必须采用这种做法，请一定严格遵守此项规范。--no-ff合并的执行结果如下图所示：
- ![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/2afed418205e184dc58906ce7fb70e7124893c84140b9c6d484f89c02c217bad.png)
- 2）预发布分支(release)
- 指发布正式版本之前（即合并到master分支之前），我们可能需要有一个预发布的版本进行测试。预发布分支是从develop分支上面分出来的，预发布结束以后，必须合并进develop和master分支。该分支命名规则参考章节1.3.4.5。
- 创建一个预发布分支：
- git checkout -b release-1.2.2.0 develop
- 测试确认没有问题后，合并到master主干，并做一个标签
- git checkout master
- git merge --no-ff release-1.2.2.0
- # 对合并生成的新节点，做一个标签
- git tag -a 1.2.2.123456
- 再合并到develop分支：
- git checkout develop
- git merge --no-ff release-1.2.2.0

最后，删除预发布分支：

- git branch -d release-1.2.2.0
- 3）hotfix分支
- 正式发布以后，难免会出现bug。这时就需要创建一个分支，进行bug修复。修复bug分支是从master分支上面分出来的。修复结束以后，再合并进master和develop分支。它的命名采用hotfix-*的形式，该分支命名规则参考章节1.3.4.6。

- 创建一个修复bug分支：
- git checkout -b hotfix-1.2.3.0 master
- 修复结束后，合并到master分支：
- git checkout master
- git merge --no-ff hotfix-1.2.3.0
- git tag -a 1.2.3.123456
- 再合并到develop分支：
- git checkout develop
- git merge --no-ff hotfix-1.2.3.0

```javascript
import axios from 'axios'
import { MessageBox, Message } from 'element-ui'
import store from '@/store'
import { getToken } from '@/utils/auth'

// create an axios instance
const service = axios.create({
  baseURL: process.env.VUE_APP_BASE_API, // 接口地址
  timeout: 50000 // 请求超时
})

// request interceptor
service.interceptors.request.use(
  config => {
    // do something before request is sent
if (store.getters.token) {
// 前端请求头加token
      config.headers['Authorization'] = getToken()
      config.headers['X-Token'] = getToken()
// 前端请求头菜单根据项目取不同的参数
      config.headers['tenantIds'] = 'common,sc'
    }
    return config
  },
  error => {
    // do something with request error
    return Promise.reject(error)
  }
)

// response interceptor
service.interceptors.response.use(
  response => {
    if (response.config.responseType === 'blob') {
      return response
    }
    // if (response.config.responseType === 'blob') { // 解决 blob请求类型 错误信息
    //   const blob = new Blob([response.data])
    //   const reader = new FileReader()
    //   reader.readAsText(blob, 'utf-8')
    //   reader.onload = function() {
    //     try {
    //       console.log(reader);
    //       const data = JSON.parse(reader.result)
    //       Message.error({ message: data.msg || '操作有误,请重新操作!' })
    //     } catch (e) {
    //       console.log(e)
    //       Message.error({ message: '系统错误请联系管理员' })
    //     }
    //   }
    // }
    const res = response.data
    if (res.code === 1 || res.code === 3019 || res.code === 3017 || res.code === 120 || res.code === 124) {
      return Promise.resolve(response)
    } else if (res.code === 111 && res.data === null || res.code === 101 || res.code === 121 || res.code === 2 || res.code === 3013) {
      Message({
        message: res.msg,
        type: 'error',
        duration: 2 * 1000
      })
    } else {
      const resetPassword1 = sessionStorage.getItem('resetPassword')
      if (res.code === 1003) {
        MessageBox.confirm(resetPassword1 === 1 ? '修改成功，请重新登录' : res.msg, {
          title: '提示',
          confirmButtonText: '重新登录',
          cancelButtonText: '取消',
          showClose: false,
          closeOnPressEscape: false,
          closeOnClickModal: false,
          type: 'warning'
        }).then(() => {
          sessionStorage.removeItem('resetPassword')
          store.dispatch('user/resetToken').then(() => {
            sessionStorage.removeItem('resetPassword')
            location.reload() // 为了重新实例化vue-router对象 避免bug
          })
        })
      } else if (res.code === 3004 || res.code === 3005 || res.code === 3003) {
        Message({
          message: res.msg,
          type: 'error',
          duration: 2 * 1000
        })
      }
      return Promise.reject(response)
    }
  },
  error => {
    Message({
      message: '服务器内部错误访问错误，请稍后刷新重试',
      type: 'error',
      duration: 2 * 1000
    })
    return Promise.reject(error)
  }
)

export default service
```

```plain
8.1.2流程说明
1.项目经理跟客户沟通完毕，了解客户需求后，发送邮件给产品经理,抄送巫传鑫，宋骐飞，郭睿。
邮件应包含以下几点：
①.详细需求文档
②.预期完成时间
③.优先级
低 中 高 紧急
紧急是特殊的情况，一般是重大缺陷或特殊需求，紧急发布测试是不充分，如有问题则进入正常迭代中。
④类型
新增需求 功能优化
2.产品经理跟项目经理沟通，需求确定无误后。和技术经理进行需求评审，该阶段会确认需求是否要做，实现难度，大致工时等。如可以实现，则技术经理会把该项需求列入开发清单，并排列开发计划。
3.确认开发计划后，技术经理回复邮件。邮件包含以下几点信息
①是否可以实现，是否要做
②能做，回复大致完成时间，更新时间
③不能做，则回复理由
4.项目经理需确认技术经理回复，如有异议。则进入会议流程，参会人如下
①项目经理
②技术经理
③产品经理
④其他项目相关人
会议商讨结果由项目经理整理邮件发布
5.更新邮件会发送给各项目经理和实施人员，项目经理需确认实施人员部署情况和系统功能状况并回复邮件
8.1.3节点补充说明
1.需求评审在星期四上午进行，星期三之后提交的会在下次需求评审会议上评审
2.产品经理需当天回复项目经理邮件
3.计划安排在星期5会由技术经理统一发布
4.系统发布前，产品要发布功能更新清单
5.正常迭代是一月发布一次，紧急发布是开发完成且测试后就发布。
```
