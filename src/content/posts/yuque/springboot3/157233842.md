> `场景1`不是异步的。总共要执行`200ms`，将它改造成异步的并且是用监听机制会好很多。不要纠结这个时间。

### 2.解耦![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/c84cb49a941f0ea6cc1095e1c018a7a8337a0bf83cd0f9f6d3aad66f9d01e5c9.png)

> `场景2`如果是调用对应接口的话，如果库存系统的接口`有变化`，那么订单系统对接口的调用也有变化。我们直接使用`消息队列`代替`接口调用`。

### 3.削峰![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/a96860b34f1f7519aebf350082031376fc3b56f48ace31f89bd329f5aed8f861.png)

> 如果一个`短时间`有很多`用户请求`发给`服务器`的话，`服务器`一下子处理不过来就会`宕机卡死`，为了防止这种情况，我们将所有的`用户请求`放在`队列`中。放`服务器`慢慢解决队列中的请求。保证不会出现峰值宕机的情况。

### 4.缓冲![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/38af6536ce6f9a2eb50248fce9ccea795dd1754545f14af46860c403a4d66ec6.png)

> 和削峰差不多，也是防止过多请求导致的服务器宕机。

## 消息队列-Kafka

### 1. 消息模式

## ![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/56aceef50f99283839f484570d336be53fa90b9ca206cb47af4624c899fc4f7b.png)

> 点对点：
> 1. 发送消息
> 2. 接受消息
> 3. 给队列发送确认收到的信息
> 4. 队列删除已处理的信息
> 发布订阅：
> 1. 订阅者不会给队列发送确认收到的信息，因为不能该订阅者接收到了消息就删除该消息了，还有其他订阅者呢。
> 2. 每一个订阅者都有一个 `offset` 队列偏移，每个消费者有重复消费同一个消息。标识因该接收队列中 `第几条` 消息了。因为队列没有删除消息嘛。如果是消费者组，那就是一个消费者组共用一个offset,组内没有重复消费。
> 3. 一个消息队列可以有多个 `主题` ，像 `news、tech` 等主题。

### 2. Kafka工作原理![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/1abd86a355df7232fc288441ff51a5ba37368d84acbcdaddcd410a4cf0cae510.png)

> 1. `100T` 的主题为 `news` 的数据分给 `三个` 分区存储。选择哪一个可能是用 `取余` 的方法。这样就减轻了 `kafka` 服务器的存储压力。而不是三个生产者向同一个partition中存入数据，压力很大。并且如果三个partition都在同一个机器里面（也就是partition1 partition2 partition3）然后多个生产者向三个partition存入topic为news的100T的数据。这使得CPU压力很大。大部分CPU都去执行这多个生产者的写入队列的命令去了。因此我们引入broker, 将三个partition 存入三个broker中（这里我们没有考虑消息顺序的问题，或许使用取余来解决），这样机器的写入队列操作就分散到3个机器中了。但是如果一个机器炸了，它存放的partition就没有了，因此会在其余两个机器上存放副本。因此本来存储news的一个队列，变成了存放news的partitions的三个队列，订阅news的消费者就消费这三个队列。但是假如有3个消费者（服务集群中的3个服务实例）共同分担消费news，命令 `消费者1` 只能访问 `分区0` ； `消费者2` 只能访问 `分区1` ； `消费者3` 只能访问 `分区2` 。因为不会删除被消费过的消息，如果我们再添加 `消费者4` ，为了防止消息的重复消费，它必定是延续还未消费的offset进行下一个消息的竞争，然后消费（不保证顺序，我觉得要保证顺序，就4个消费者一同竞争然后1个获取到锁，就可以进行消费）。因为是延续offset，之前被消费过的消息就不会被消费了，因此我们有了消费者组，不同消费者组，他们的offset不一致，可以最初又开始消费。
> 2. 为了防止存储器损坏，数据丢失。 `Kafka` 会有副本存储机制。使用 `Zookeeper` 来管理副本。就像上图， `topic-news partition-0` 在 `分区1` 和 `分区2` 中也有对应的副本。加上原数据总共有 `3` 个副本。
> 3. 同一个消费者组里面的消费者是队列竞争模式。同组有 `消费者1，2，3` ， `消费者1` 只能访问 `分区0` ； `消费者2` 只能访问 `分区1` ；消费者3只能访问分区2。如果在多一个 `消费者4` 就进行竞争消费。
> 这样是不保证消费顺序的。
> 4. 不同消费者组里面的消费者就是发布/订阅模式。

> `KafkaAutoConfiguration`自动配置类

```java
@AutoConfiguration
@ConditionalOnClass({KafkaTemplate.class})
@EnableConfigurationProperties({KafkaProperties.class})
@Import({KafkaAnnotationDrivenConfiguration.class, KafkaStreamsAnnotationDrivenConfiguration.class})
public class KafkaAutoConfiguration {}
```

```java
/**
 * KafkaAutoConfiguration提供如下功能
 * 1、KafkaProperties：kafka的所有配置; 以 spring.kafka开始
 *    - bootstrapServers: kafka集群的所有服务器地址
 *    - properties: 参数设置
 *    - consumer: 消费者
 *    - producer: 生产者
 *    ...
 * 2、@EnableKafka: 开启Kafka的注解驱动功能
 * 3、KafkaTemplate: 收发消息
 * 4、KafkaAdmin： 维护主题等...
 * 5、@EnableKafka +  @KafkaListener 接受消息
 本来@EnableKafka标注在入口程序上才能让@KafkaListener生效。但好像不用@EnableKafka也行。
 *    1）、消费者来接受消息，需要有group-id
 *    2）、收消息使用 @KafkaListener + ConsumerRecord
 *    3）、spring.kafka 开始的所有配置
 * 6、核心概念
 *    分区：  分散存储，1T的数据分散到N个节点
 *    副本：  备份机制，每个小分区的数据都有备份
 *    主题： topics； 消息是发送给某个主题
 */
```

#### 3.监听消息

```java
@Component
public class MyHahaTopicListener {

    //默认的监听是从消息队列最后一个消息开始拿。新消息才能拿到
    @KafkaListener(topics="newshaha",groupId="haha")
    public void haha(ConsumerRecord record){
        //1、获取消息的各种详细信息
//        String topic = record.topic();
        Object key = record.key();
        Object value = record.value();
        System.out.println("收到消息：key【"+key+"】 value【"+value+"】");
    }
}
```
