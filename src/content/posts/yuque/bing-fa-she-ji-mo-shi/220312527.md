### **一、故事背景**

小菜被告知生产环境社区电商系统的优惠券服务内存和CPU占用都非常高，服务器处于假死状态。于是，小菜将社区电商系统的优惠券服务拉取下来，发现程序中会为每条消息的推送都会创建一个线程来执行，他第一时间想到的就是使用线程池，但有想到推送消息的效率问题，或者说是尽可能快的将消息推送出去，小菜使用了代码Executors.newCachedThreadPool()来创建线程池，没想到这次服务器的CPU又爆了。在无奈的情况下，小菜决定还是请教老王，让老王为其分析下遇到的问题，老王也为小菜耐心的进行了讲解。

### **二、复现代码**

### **三、分析Executors类**

在分析小菜遇到的CPU占用高的问题之前，我们先来分析下Executors类中创建线程池的方法，因为小菜本身就是使用Executors类中的newCachedThreadPool()方法来创建线程池的，在Executors类中，提供了大量创建线程池的方法，如下所示。

**（1）Executors.newCachedThreadPool()方法**

创建一个可缓存的线程池，如果线程池中存在的线程数量超过程序处理的需要，则线程池可以根据具体情况灵活回收空闲的线程。如果向线程池提交任务时，线程池中没有空闲的线程，则新建线程处理任务。

**（2）Executors.newFixedThreadPool()方法**

创建一个定长的线程池，可以控制线程池中线程的最大并发数。向线程池提交任务时，如果线程池中有空闲线程，则分配一个空闲线程执行任务。如果线程池中没有空闲线程，则将提交的任务放入阻塞队列中等待。

**（3）Executors.newScheduledThreadPool()方法**

创建一个支持定时、周期性执行任务的线程池。

**（4）Executors.newSingleThreadExecutor()方法**

创建内部只有一个线程的线程池，线程池内部使用一个唯一的线程执行任务，提交到线程池中的任务都会按照先到先处理的原则串行执行。

**（5）Executors.newSingleThreadScheduledExecutor()方法**

创建内部只要一个线程，并且支持定时、周期性执行任务的线程池。

**（6）Executors.newWorkStealingPool()方法**

从JDK1.8版本开始提供的方法，底层使用的是 ForkJoinPool 实现，创建一个拥有多个任务队列的线程池，可以实现任务的并行执行。

使用Executors.newFixedThreadPool()方法和Executors.newSingleThreadExecutor()方法创建线程池时，由于内部阻塞队列使用的是LinkedBlockingQueue的默认构造方法进行初始化，默认的LinkedBlockingQueue队列的长度时Integer.MAX_VALUE，使用Executors.newFixedThreadPool()方法和Executors.newSingleThreadExecutor()方法创建的线程池在高并发环境下容易发生内存泄露的问题。

另外，在高并发环境下使用Executors.newCachedThreadPool()方法创建的线程池容易导致CPU占用100%的问题。

### **四、分析问题**

复现小菜的代码并分析了Executors类后，我们再来分析下小菜遇到的问题。其实，本质上小菜遇到的问题还是使用了Executors.newCachedThreadPool()方法来创建线程池导致的，那为什么使用Executors.newCachedThreadPool()方法创建线程池，在大并发场景下就会出现无法创建本地线程的异常呢？

#### **4.1 分析newCachedThreadPool()方法**

首先打开Executors类的newCachedThreadPool()方法的源码，源码详见：[java.util.concurrent.Executors#newCachedThreadPool](http://java.util.concurrent.Executors#newCachedThreadPool)()。

```go
public static ExecutorService newCachedThreadPool() {
  return new ThreadPoolExecutor(0, Integer.MAX_VALUE,
                 60L, TimeUnit.SECONDS,
                 new SynchronousQueue<Runnable>());
}
```

可以看到，使用Executors.newCachedThreadPool()方法创建的线程池，核心线程数为0，也就是说，当线程池中的线程全部空闲，1分钟内没有执行任务时，都可以被回收。但是，不知道大家注意到没有，这种线程池虽然核心线程数为0，但是最大线程数却为Integer.MAX_VALUE。可以认为最大线程是没有上限的，而任务队列SynchronousQueue是一个没有空间的阻塞队列，此时只要有一个任务到来，就必须要有一个线程来处理，如果当前没有空闲的线程处理任务，则会创建一个新的线程来处理任务。

如果程序中执行了耗时的任务，向小菜处理的向用户APP推送消息的逻辑，因为是调用了其他的独立服务，存在跨网络调用的问题，所以是一个比较耗时的操作，当大量用户下单成功，调用推送消息服务的并发量上来，就会创建大量的线程来调用推送消息的服务，此时就可能会抛出[java.lang.OutOfMemoryError:](http://about:blank)unable to create new native thread异常，这就是无法创建新的本地线程的异常。

那有小伙伴可能会问：那既然使用Executors.newCachedThreadPool()方法创建线程池，会创建大量的线程导致抛出异常。那我使用Executors.newFixedThreadPool()方法创建线程池总行了吧，这个方法创建的线程池会固定线程数，这样就没问题了吧？

真的是这样吗？我们继续分析。

#### **4.2 分析newFixedThreadPool()方法**

我们还是打开Executors类的newFixedThreadPool()方法，源码详见：[java.util.concurrent.Executors#newFixedThreadPool](http://java.util.concurrent.Executors#newFixedThreadPool)(int)。

```go
public static ExecutorService newFixedThreadPool(int nThreads) {
  return new ThreadPoolExecutor(nThreads, nThreads,
                 0L, TimeUnit.MILLISECONDS,
                 new LinkedBlockingQueue<Runnable>());
}
```

虽然Executors类的newFixedThreadPool()方法会通过传入线程数量来控制创建的线程数，但是这种线程池使用的任务队列却是LinkedBlockingQueue，我们再打开LinkedBlockingQueue的无参构造函数。

源码详见：[java.util.concurrent.LinkedBlockingQueue#LinkedBlockingQueue](http://java.util.concurrent.LinkedBlockingQueue#LinkedBlockingQueue)()。

```go
public LinkedBlockingQueue() {
  this(Integer.MAX_VALUE);
}
```

看到这里，大家明白了，虽然使用Executors类的newFixedThreadPool()方法创建的线程池可以使用固定数量的线程来执行任务，但是其使用的任务队列却是无界阻塞队列。如果并发执行的任务很多，要执行的任务量很大，这些任务就会不断添加到LinkedBlockingQueue队列中，积累到一定量时，就会撑爆内存导致OOM问题，最终会抛出[java.lang.OutOfMemoryError:](http://about:blank)GC overhead limit exceeded异常。

回到小菜处理的消息推送业务，同样由于在社区电商系统中，会跨网络调用消息推送的服务，由于网络的不稳定性，这种操作本身就是比较耗时的，再加上业务体量比较大，如果下单成功的人数比较多，并发量上来，很容易就出现OOM的问题。所以，处理小菜遇到的问题时，既不能使用Executors类的newCachedThreadPool方法创建线程池，也不能使用Executors类的newFixedThreadPool()方法创建线程池。
