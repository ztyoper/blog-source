“在真正实现不可变模式之前，为了加深你对不可变模式在实际项目场景的理解，我们看看不使用不可变模式实现的话，存在哪些问题”，老王说。

#### **3.1 封装消息实体类**

首先是封装消息对象的MessageInfo类，MessageInfo类的源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.example.wrong.MessagInfo](http://io.binghe.concurrent.design.example.wrong.MessagInfo)。

```go
public class MessageInfo {
    /**
    * 设备编号
    */
    private String deviceCode;
​
    /**
    * 第三方消息推送的接口
    */
    private String messageUrl;
​
    public MessageInfo(String deviceCode, String messageUrl) {
        this.deviceCode = deviceCode;
        this.messageUrl = messageUrl;
    }
    /***********省略setter/gettter*************/
}
​
```

可以看到，在MessagInfo的实现中，MessagInfo类本身以及各成员变量并未使用final关键字修饰，并且提供了修改成员变量的方法，所以，MessagInfo类并不是一个不可变类。

#### **3.2 实现发送消息路由**

接着，老王又写了一个发送消息的路由类MessagRouter，MessagRouter类的源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.example.wrong.MessagRouter](http://io.binghe.concurrent.design.example.wrong.MessagRouter)。

```go
public class MessagRouter {
​
    /**
    * 实例化一个消息路由对象，为了在多个线程间可见，使用volatile关键字修饰
    */
    private static volatile MessagRouter instance = new MessagRouter();
​
    /**
    * 存储消息推送服务商的Map, Key表示推送消息时的路由标识
    */
    private final Map<String, MessageInfo> messageInfoMap;
​
    public MessagRouter(){
        this.messageInfoMap = this.loadMessageInfoMap();
    }
​
    /**
    * 模拟从数据库加载数据
    */
    private Map<String, MessageInfo> loadMessageInfoMap() {
        Map<String, MessageInfo> map = new HashMap<>();
        map.put("jiguang", new MessageInfo("1001", "https://www.jiguang.cn"));
        map.put("xinge", new MessageInfo("1002", "https://www.xinge.cn"));
        map.put("umeng", new MessageInfo("1003", "https://www.umeng.com"));
        return map;
    }
​
    public Map<String, MessageInfo> getMessageInfoMap() {
        return messageInfoMap;
    }
}
```

在MessagRouter类中，首先定义了一个使用volatile修饰的静态路由实例instance，并且定义了一个final修饰的成员变量messageInfoMap，用来存储不同消息推送服务商的信息，Key表示推送消息路由标识，Value就是发送消息的实体对象，并且在MessagRouter类的构造方法中，就会调用loadMessageInfoMap()方法模拟从数据库中查询数据，存入messageInfoMap中。同时，在MessagRouter类中还提供了一个返回messageInfoMap的getMessageInfoMap()方法。

“如果消息推送服务商的信息发生变更，在逻辑上就会先更新数据库，在更新内存中的信息”，说着，老王又写了一个updateRoute()方法，如下所示。

```go
public void updateRoute(String routeKey, String deviceCode, String messageUrl){
    Map<String, MessageInfo> map = instance.getMessageInfoMap();
    MessageInfo messageInfo = map.get(routeKey);
    messageInfo.setDeviceCode(deviceCode);
    messageInfo.setMessageUrl(messageUrl);
    map.put(routeKey, messageInfo);
}
```

其实，这个updateRoute()方法也会暴露很多问题，最明显的就是更新设备编号和更新推送消息url不是一个原子操作，很可能刚刚更新完设备编号，此时另一个线程就过来读取数据了，造成数据不一致的问题。

举个例子：假设需要更新messageInfoMap中routeKey为jiguang的数据，将设备编号更新成1004，推送消息的url更新成[https://www.jiguang.com](https://www.jiguang.com)，由于在updateRoute()方法中，设置deviceCode的操作与设置messageUrl的操作不是原子操作，很可能一个线程设置完deviceCode的值，恰好另一个线程过来读取routeKey为jiguang的数据，此时读取到的数据就是设备编号为1004，推送url为[https://www.jiguang.cn](https://www.jiguang.cn)，与期望的设备编号为1004，推送url为[https://www.jiguang.com](https://www.jiguang.com)不一致，这样就会出现消息推送的问题。

### **四、改造成不可变模式**

了解了不使用不可变模式实现的代码存在的一些问题后，老王又开始基于不可变模式改造代码，避免出现线程安全问题，并且耐心的为小菜分步骤进行讲解，具体的修改步骤如下所示。

#### **4.1 修改MessageInfo类**

修改MessageInfo类，使其变成一个不可变类，修改后的MessageInfo类源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.example.right.MessageInfo](http://io.binghe.concurrent.design.example.right.MessageInfo)。

#### **4.2 修改MessagRouter类**

修改后的MessagRouter类的源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.example.right.MessagRouter](http://io.binghe.concurrent.design.example.right.MessagRouter)。

这里，分步骤讲解如何修改MessagRouter类，最终达到线程安全的目的。

**第一步**：对返回messageInfoMap对象的getMessageInfoMap()方法进行防御性复制，如下所示。

```go
public Map<String, MessageInfo> getMessageInfoMap() {
    return Collections.unmodifiableMap(cloneMessageInfoMap(messageInfoMap));
}
​
private Map<String, MessageInfo> cloneMessageInfoMap(Map<String, MessageInfo> map){
    Map<String, MessageInfo> cloneMap = new HashMap<>();
    for (Map.Entry<String, MessageInfo> entry : map.entrySet()){
        cloneMap.put(entry.getKey(), entry.getValue());
    }
    return cloneMap;
}
```

可以看到，在getMessageInfoMap()方法中，对返回的messageInfoMap方法进行了防御性复制，防止其他类获取到messageInfoMap后，修改MessagRouter类中本身的messageInfoMap对象的数据。

**第二步**：提供获取和设置整个MessagRouter路由实例的方法，如下所示。

```go
public static MessagRouter getInstance(){
    return instance;
}
​
public static void setInstance(MessagRouter newInstance){
    instance = newInstance;
}
```

**第三步：**修改updateRoute()方法来模拟更新数据，如下所示。

```go
public void updateRoute(String routeKey, String deviceCode, String messageUrl){
    //模拟更新数据库数据
    updateMessageInfoFromDb(routeKey, deviceCode, messageUrl);
    //以替换整个MessagRouter实例的方法刷新缓存
    MessagRouter.setInstance(new MessagRouter());
​
}
```

这样，当变更消息推送服务商时，会调用updateRoute()方法，首先更新数据库中的数据，随后以替换整个MessagRouter实例的方式来刷新缓存中的消息推送服务商的信息。并且在设置MessagRouter实例时，会调用MessagRouter的构造方法传入一个新的对象，此时就会调用loadMessageInfoMap()方法从数据库中加载消息推送服务商的信息。此时整个过程就是线程安全的了。

### **五、本章总结**

本章，以案例的形式进一步讲解了不可变模式在实际项目过程中的落地实现方案，并且再次对比了不使用不可变模式存在的问题，以及使用不可变模式为何能解决线程安全问题。总之，在使用不可变模式时，一定要基于如下原则：

（1）必须使用final关键字修饰不可变类，禁止被其他类继承，防止子类改变其方法和行为。

（2）必须使用final关键字修饰类中的所有成员变量，避免成员变量被修改。使用final修饰成员变量，也能保证成员变量在多线程并发环境下被其他线程访问时，一定是初始化完成的。

（3）必须使用private关键字修饰所有成员变量，防止子类和其他类通过成员变量的引用改变变量值。

（4）类中禁止提供修改内部状态的公开方法。

（5）创建对象的过程中，this关键字不能泄露给其他类，防止其他类（比如这个类的匿名内部类）在对象创建过程中修改状态。

（6）类中的任何字段，如果引用了状态可变的对象，比如集合、数组等，则这些字段也必须使用private修饰，这些字段以及字段的引用不能对外暴露，返回这些字段值时，必须进行防御性复制。
