主动对象模式在异步模式的基础上进一步分离了方法的调用和方法的执行。如果使用串行模式执行业务逻辑时，可能会存在一些不可避免的问题，此时我们就可以使用主动对象模式，将业务逻辑的请求信息缓存起来，待问题修复后，即可重新发起请求。基于此，我们可以对社区电商项目进一步优化。

### **一、故事背景**

整个故事的主人公小菜，也就是我们的菜哥，在为社区电商项目商品添加短链接功能时，出现了访问商品404的问题。随后找老王分析问题所在，并且老王也为其介绍了使用主动对象模式能够解决小菜遇到的问题，不仅如此，老王还为小菜详细介绍了什么是主动对象模式，对主动对象模式的类结构和执行流程进行了详细的介绍。随后，就是要基于主动对象模式来优化社区电商系统了。

### **二、回顾问题**

在小菜实现长短链接转换的功能时，采用了串行化的执行方案，根据长链接生成短链接后，就会将长短链接的映射关系存储起来。其实，其实，对于我们后端程序员来说，数据的存储操作，像数据库等等不是任何时刻都是100%高可用的，对于运营来说，按照现有的实现方案来讲，如果运营在发布商品时，存储长短链接映射关系的服务出现问题，轻则无法存储长短链接的映射关系，重则根本无法正常发布商品，如图33-1所示。

对于用户来说。如果用户在浏览商品时，一旦存储长短链接的服务出现问题，那就无法根据短链接正确的查询出长链接。最终造成访问不到资源的问题，如图33-2所示。

### **三、解决思路**

对于运营或者商家来说，如果在基于长链接转换成短链接失败，或者存储长短链接的映射关系失败时，提示运营或者商家发布商品失败，但是这种提示对于商家或者运营来说，就非常不友好了。本身为商品资源数据生成短链接从整个流程上来说，对用户就不是非常核心的功能，用户只要能正常访问到商品就行。

此时，如果发布商品时，基于长链接转换短链接失败或者存储长短链接的映射关系失败，可以将请求的信息存储起来，等待故障恢复后，再继续执行长链接转换短链接的逻辑和存储长短链接的映射关系。此时，直接为用户端返回商品资源信息的长链接，后续用户直接根据长链接访问商品即可，这也是一种服务降级的策略，此时对于运营或者商家端来说，系统的执行流程如图33-3所示。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/f9e9510bfe5239ef0060f5055cf2d9b6c20c34e5f7e6819b12ea2abb948e25d1.png)

可以看到，对于运营或者商家端来说，将长链接转换成短链接，存储长短链接的映射关系，一般都会部署成单独的服务，发布商品时，如果转换短链接或者存储长短链接的映射关系失败，就会将请求的信息存储起来，当转换长短链接的服务或者存储长短链接映射关系的服务恢复后，再由转换长短链接的服务读取存储的请求信息，将长链接转换成短链接后，将其映射关系存储起来。

此时，对于用户端来说，打开浏览器点击商品时，就会直接根据长链接来获取商品的资源信息，如图33-4所示。

![](https://pub-ccd5622eabb54b4a81678003778ddce1.r2.dev/PicGo/353ddd3ca0e229893a2a7bb30eedd5a2d88a5a657296e0763decd3bc13137e45.png)

可以看到，此时服务会直接降级为通过长链接获取商品的资源数据。

### **五、代码实现**

本节，我们主要是实现基于主动对象模式优化社区电商系统最核心的代码，具体实现步骤如下所示。

**（1）实现RequestStore接口**

RequestStore接口是存储请求数据的接口，源码详见：[io.binghe.concurrent.design.active.object.right.RequestStore](http://io.binghe.concurrent.design.active.object.right.RequestStore)。

```go
public interface RequestStore extends Closeable {
  void flush(GoodsRequest goodsRequest);
}
```

可以看到， RequestStore接口继承了Closeable接口，并定义了一个刷新请求到存储的flush()方法。

**（2）实现DBRequestStore类**

DBRequestStore类实现了RequestStore接口，是真正执行保存请求信息的方法，源码详见：[io.binghe.concurrent.design.active.object.right.DBRequestStore](http://io.binghe.concurrent.design.active.object.right.DBRequestStore)。

```go
public class DBRequestStore implements RequestStore {
  @Override
  public void flush(GoodsRequest goodsRequest) {
    System.out.println("保存请求到数据库开始");
    long startTime = System.currentTimeMillis();
    try {
      Thread.sleep(1000);
     } catch (InterruptedException e) {
      e.printStackTrace();
     }
    System.out.println("保存请求到数据库完毕，存储的数据为：" + goodsRequest.toString());
    System.out.println("保存请求到数据库结束，耗时：" + (System.currentTimeMillis() - startTime) + "ms");
   }
​
  @Override
  public void close() throws IOException {
    // ignore
   }
}
```

可以看到，在DBRequestStore类中实现的flush()方法中，模拟实现了保存请求信息的操作。

**（3）实现ProxyRequestStore类**

ProxyRequestStore同样实现了RequestStore接口，并且是DBRequestStore类的代理类，源码详见：[io.binghe.concurrent.design.active.object.right.ProxyRequestStore](http://io.binghe.concurrent.design.active.object.right.ProxyRequestStore)。

```go
public class ProxyRequestStore implements RequestStore {
​
  private static final RequestStore INSTANCE = new ProxyRequestStore();
​
  public static RequestStore getInstance(){
    return INSTANCE;
   }
  private ProxyRequestStore(){}
​
  private final ThreadPoolExecutor scheduler = new ThreadPoolExecutor(3,3,1,
                    TimeUnit.HOURS,
                    new ArrayBlockingQueue<>(256),
                    r -> new Thread(r, "scheduler-thread"), new ThreadPoolExecutor.CallerRunsPolicy());
  private final RequestStore requestStore = new DBRequestStore();
​
  @Override
  public void flush(GoodsRequest goodsRequest) {
    Callable<Boolean> methodRequest = () -> {
      System.out.println("调度执行缓冲区中的MethodRequest请求");
      requestStore.flush(goodsRequest);
      return Boolean.TRUE;
     };
    System.out.println("将MethodRequest请求放入缓冲区");
    scheduler.submit(methodRequest);
   }
​
  @Override
  public void close() throws IOException {
    scheduler.shutdown();
   }
}
```

可以看到，ProxyRequestStore类不仅实现了RequestStore接口，还是一个单例类，并且会通过异步的方式代理DBRequestStore类的对象。在ProxyRequestStore类实现的flush()方法中，会通过线程池的方式来异步执行DBRequestStore类对象的flush()方法，由于线程池会自带任务队列，所以，这里是借助线程池实现的主动对象模式。并且在DBRequestStore类中实现了Closeable接口的close()方法，在close()方法中关闭线程池。

**（4）实现URLService接口**

URLService接口是URL业务接口，源码详见：[io.binghe.concurrent.design.active.object.right.URLService](http://io.binghe.concurrent.design.active.object.right.URLService)。

```go
public interface URLService {
  String getShortUrlByGoodsRequest(GoodsRequest goodsRequest);
}
```

可以看到， 在URLService接口中定义了一个根据GoodsRequest对象获取短链接的方法，也就是模拟生产短链接。

**（5）实现URLServiceImpl类**

URLServiceImpl类是URLService接口的实现类，源码详见：[io.binghe.concurrent.design.active.object.right.URLServiceImpl](http://io.binghe.concurrent.design.active.object.right.URLServiceImpl)。

```go
public class URLServiceImpl implements URLService {
  @Override
  public String getShortUrlByGoodsRequest(GoodsRequest goodsRequest) {
    String shortUrl = null;
    try{
      shortUrl = this.getShortUrlByLongUrl(goodsRequest.getLongUrl());
     }catch (Exception e){
      System.out.println(e.getMessage());
      System.out.println("执行异步存储请求的操作");
      ProxyRequestStore.getInstance().flush(goodsRequest);
     }
    return shortUrl;
   }
​
  private String getShortUrlByLongUrl(String longUrl){
    //模拟抛出异常
    throw new RuntimeException("转换短链接失败，当前传递的长链接为：" + longUrl);
   }
}
```

可以看到，在URLServiceImpl类实现的getShortUrlByGoodsRequest()方法中，会首先调用getShortUrlByLongUrl()方法模拟生成短链接，由于getShortUrlByLongUrl()方法会抛出异常，所以在getShortUrlByGoodsRequest()方法中会执行catch(){}代码块中的逻辑，此时就会以主动对象模式执行异步保存请求信息的逻辑。

至此，基于主动模式实现的代码案例基本就完成了。

### **六、代码测试**

这里，为了更好的测试基于主动对象模式实现的代码案例，这里，我们实现了GoodsTest类，源码详见：[io.binghe.concurrent.design.active.object.right.GoodsTest](http://io.binghe.concurrent.design.active.object.right.GoodsTest)。

```go
public class GoodsTest {
  public static void main(String[] args) {

    GoodsRequest goodsRequest = new GoodsRequest("http://binghe.com/xxx/xxx/xxx/xxx/xxx/xxx/xxx/xxx");
```

可以看到，GoodsTest类的逻辑就比较简单了，主要就是封装GoodsRequest类的对象，通过调用urlService对象的getShortUrlByGoodsRequest()方法类生成短链接。运行GoodsTest类的main()方法，输出的结果信息如下所示。

