### **三、不可变类的原则**

二人走到会议室后，老王放下电脑后说到：“我先给你讲讲写不可变类必须要满足的条件，也就是不可变类必须要遵循的原则”。

“好的”，小菜回应道。

“说起不可变类，必须要遵循。。。”，老王巴拉巴拉的说起来。

总体上讲，老王总结了如下几点：

（1）必须使用final关键字修饰不可变类，禁止被其他类继承，防止子类改变其方法和行为。

（2）必须使用final关键字修饰类中的所有成员变量，避免成员变量被修改。使用final修饰成员变量，也能保证成员变量在多线程并发环境下被其他线程访问时，一定是初始化完成的。

（3）必须使用private关键字修饰所有成员变量，防止子类和其他类通过成员变量的引用改变变量值。

（4）类中禁止提供修改内部状态的公开方法。

（5）创建对象的过程中，this关键字不能泄露给其他类，防止其他类（比如这个类的匿名内部类）在对象创建过程中修改状态。

（6）类中的任何字段，如果引用了状态可变的对象，比如集合、数组等，则这些字段也必须使用private修饰，这些字段以及字段的引用不能对外暴露，返回这些字段值时，必须进行防御性复制。

### **四、实现不可变类**

“不可变类之前我们也说过，它就是一经创建就不会再被改变的类”，老王边说边开始敲代码。

“首先，按照不可变类的原则来讲，我们先给User类和它的成员变量name与idCard都使用final关键字修饰，此时在User类中就会报错，要去掉set()方法，添加一个构造方法”，说话间，老王就将修改后的User类敲出来了（老王真牛）。

User类的源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.demo.right.User](http://io.binghe.concurrent.design.demo.right.User)。

```go
public final class User {
    private final String name;
    private final Long idCard;
    public User(String name, Long idCard) {
        this.name = name;
        this.idCard = idCard;
    }
    @Override
    public String toString() {
        return "User{" +
                "name='" + name + '\'' +
                ", idCard=" + idCard +
                '}';
    }
}
```

“这样User类就不能被其他类继承，也就是说，User类不会有任何子类来改变它的方法和行为，并且User里的成员变量都是使用final关键字修饰，也不会有其他方法来修改成员变量的值，User类能结合不可变类的原则看懂吗？”，老王继续说道。

“嗯，这里可以看懂”，小菜回应道。

“接下来，我们再来看TicketCheck类，之前你写的TicketCheck类的updateUser()方法中会分别传入userName和idCard来修改通过检票的人”，说着，老王打开了之前小菜写的代码，如下所示。

```go
public class TicketCheck {

    private Map<String, User> userMap = new ConcurrentHashMap<>();

```

“我们不能这么写TicketCheck类了”，老王继续说：“结合不可变类的原则时，我们需要在TicketCheck类的updateUser()方法中直接传入User对象”，说着老王修改了TicketCheck类的源码。

修改后的TicketCheck类的源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.demo.right.TicketCheck](http://io.binghe.concurrent.design.demo.right.TicketCheck)。

```go
public class TicketCheck {

        return userMap.get(userKey);

```

“这样，检票的人发生变化时，可以通过替换整个User类来避免线程安全的问题，修改后的TicketCheck类能看懂吗？”，老王继续问小菜。

### **五、防御性复制**

“其实防御性复制很简单，防御性复制就是说一个类中的任何字段，如果引用了状态可变的对象，比如集合、数组等，则这些字段也必须使用private修饰，这些字段以及字段的引用不能对外暴露，返回这些字段值时，必须进行防御性复制。这里，我们还是以你写的检票场景的demo为例”，老王对小菜说，

”接下来，我们在TicketCheck类中增加一个返回userMap的getUserMap()方法和一个打印userMap的printUserMap方法“，说着老王便将TicketCheck方法进行了修改，如下所示。

```go
public class TicketCheck {
​
    private Map<String, User> userMap = new ConcurrentHashMap<>();
​
    public void updateUser(String userKey, User user){
        System.out.println(Thread.currentThread().getName() + "--当前检票的用户是：" + user.toString());
        userMap.put(userKey, user);
    }
​
    public User getUser(String userKey){
        return userMap.get(userKey);
    }
​
    public Map<String, User> getUserMap(){
        return userMap;
    }
​
    public void printUserMap(){
        System.out.println("当前userMap为===>>" + userMap);
    }
}
```

“这个类能看懂吧？”，老王继续问小菜。

”能看懂“，小菜回应道。

“好，那我们写个测试类TicketCheckTest来测一下”，说着老王便噼里啪啦的敲起了键盘，不到一分钟，写出了TicketCheckTest。

TicketCheckTest类的源码详见：concurrent-design-patterns-immutable工程下的[io.binghe.concurrent.design.demo.right.TicketCheckTest](http://io.binghe.concurrent.design.demo.right.TicketCheckTest)。

```go
public class TicketCheckTest {
​
    @Test
    public void testTicketCheck(){
        TicketCheck ticketCheck = new TicketCheck();
        ticketCheck.updateUser("1001", new User("张三", 1001L));
        ticketCheck.updateUser("1002", new User("李四", 1002L));
        //第一次打印userMap
        ticketCheck.printUserMap();
​
        Map<String, User> userMap = ticketCheck.getUserMap();
        userMap.put("1003", new User("王五", 1003L));
​
        //第二次打印userMap
        ticketCheck.printUserMap();
    }
}
```

老王继续对小菜说：“TicketCheckTest类也比较简单，就是定义一个testTicketCheck()方法，基于Junit进行测试，在testTicketCheck()方法中，创建ticketCheck对象，并通过ticketCheck对象的updateUser()方法传入name为张三和李四的用户，随后第一次打印userMap的结果。然后，通过ticketCheck对象的getUserMap()方法获取userMap对象，通过userMap对象添加name为王五的用户，随后第二次打印userMap的结果，能看懂吧？”。

“能看懂”，小菜说。

“好的，那我们运行下这个测试类，看看得出什么结果”。

于是老王在开发环境中运行了下TicketCheckTest类的testTicketCheck()方法，输出的结果数据如下所示。

```go

main--当前检票的用户是：User{name='李四', idCard=1002}
当前userMap为===>>{1002=User{name='李四', idCard=1002}, 1001=User{name='张三', idCard=1001}}
当前userMap为===>>{1003=User{name='王五', idCard=1003}, 1002=User{name='李四', idCard=1002}, 1001=User{name='张三', idCard=1001}}
```

“从输出的结果信息来看，第一次打印的结果数据中没有王五，而第二次输出的结果信息中有王五了，说明通过ticketCheck对象的getUserMap()方法获取到的userMap对象能够改变ticketCheck对象内部的userMap，因为通过ticketCheck对象的getUserMap()方法获取到的userMap对象，与ticketCheck对象内部的userMap是同一个引用。这么说明白吗？”，老王继续问道。

“明白”，小菜继续回应，一边回答一边在自己的电脑上记录着。

“好，那我们对这个TicketCheck类中的userMap集合进行防御性复制，在实现上也比较简单，JDK中的Collections类提供了进行防御性复制的方法，其实就是使用Collections中的unmodifiableMap、unmodifiableSet和unmodifiableList等方法返回一个不可修改的集合，这样当返回一个不可修改的集合时，如果拿到这个集合后修改集合内的元素就会抛出异常，以达到保护不可变类中集合的目的“，老王继续说着。

“我们修改下TicketCheck类中的getUserMap()方法”，话还没说完，老王就已经修改完了TicketCheck类中的getUserMap()方法。

```go
public Map<String, User> getUserMap(){
    return Collections.unmodifiableMap(new HashMap<>(userMap));
}
```

“那我们再运行下TicketCheckTest类中的testTicketCheck()方法，看看输出的结果如何”，老王一边说，一边运行程序。

```go

main--当前检票的用户是：User{name='李四', idCard=1002}
当前userMap为===>>{1002=User{name='李四', idCard=1002}, 1001=User{name='张三', idCard=1001}}
​
java.lang.UnsupportedOperationException
    at java.util.Collections$UnmodifiableMap.put(Collections.java:1457)
    at io.binghe.concurrent.design.demo.right.TicketCheckTest.testTicketCheck(TicketCheckTest.java:40)
```

“可以看到，此时向通过ticketCheck对象的getUserMap()方法获取到的userMap中添加王五数据会抛出UnsupportedOperationException，表示不支持的操作。因为通过Collections类的unmodifiableMap()方法返回的是一个不可修改的Map集合，也就是一个只读的集合，修改只读的集合就会抛出UnsupportedOperationException异常。既然不能修改获取到的集合了，那自然不可变类中的集合也是安全的，不能被修改了。这么说明白吗？”，老王继续问小菜。

“明白”，小菜回应道。
