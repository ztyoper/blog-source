# Confirm和配置重试

你已经在代码中**自定义了发送失败后的重试逻辑**（使用`CorrelationData`和`ConfirmCallback`来手动 retry），**就不需要配置文件里的**`template.retry.*`**这些内容了**，它们两个是**不同的机制，不能叠加使用**，否则逻辑会混乱、甚至可能重复重试。

---

### ✳️二者区别如下：

| 功能点 | 配置重试机制（`template.retry.*`） | 手动 confirm 回调重试（你写的） |
| --- | --- | --- |
| 生效位置 | SpringBoot 自动配置`RabbitTemplate`时生效 | 你手动调用`RabbitTemplate.convertAndSend()`并绑定回调逻辑 |
| 控制程度 | 简单自动重试（但不支持 confirm、nack 等精细处理） | 完全手动控制：如收到`nack`时的处理、重试次数、逻辑等 |
| 是否可共存 | ❌**不能共存**，否则会出现重复重试或逻辑冲突 | ✅手动 retry 更灵活 |

---

### ✅建议你选择哪种？

你已经使用如下逻辑：

```plain
java


复制编辑
cd.getFuture().addCallback(new ListenableFutureCallback<>() {
    ...
    public void onSuccess(CorrelationData.Confirm result) {
        if (result != null && !result.isAck()) {
            // 重试逻辑
        }
    }
});
```

这相当于是基于 RabbitMQ**Publisher Confirm 机制**的 nack 回调 + 手动重试，非常灵活，并且支持你自己加日志、监控、熔断等机制 ——**这是生产级推荐方式**。

---

### ✅结论：

- 你 **不需要也不建议再开启** 配置项：

```plain
yaml


复制编辑
spring:
  rabbitmq:
    template:
      retry:
        enabled: true
```

- 否则 RabbitTemplate 自己也会尝试重试发送消息，和你代码中的重试机制“打架”。

---

### 📝推荐你加一个细节：

你现在写的重试逻辑中有一点细节可以优化：

```plain
java


复制编辑
int retryCount; // 放在内部类中，每次 addCallback 都会复用旧值
```

建议改成一个“外部 final int[]”的数组方式：

```plain
java


复制编辑
final int[] retryCount = {0}; // 使用数组规避闭包变量修改限制
```

然后在回调中写成：

```plain
java


复制编辑
if (retryCount[0] >= maxRetries) {
    log.error("消息发送重试次数耗尽，发送失败");
    return;
}
retryCount[0]++;
```

---

### ✅是否需要配置文件？

**不需要启用 `spring.rabbitmq.template.retry.*` 相关配置。**

#### 原因：

- `spring.rabbitmq.template.retry.*` 控制的是： **连接失败、channel 不可用等场景下的自动重试机制** ；
- 而你如果只用 `Publisher Confirm` （也就是 `ack/nack` ）回调：

- 是 **RabbitMQ 正常接收后** 的结果；
- 不涉及连接失败场景；
- 所以这套配置跟你的需求无关。

---

### ✅建议配置（如果你只关心 confirm 回调）：

要确保的是启用 publisher confirm 和 return 模式，而不是 retry 机制：

```plain
yaml


复制编辑
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # 开启 CorrelationData confirm 机制
    publisher-returns: true             # 开启 ReturnCallback（Exchange 无法路由时触发）
```

---

### ✳️总结：

| 你做什么 | 是否需要`template.retry.*`配置 |
| --- | --- |
| 使用`Publisher Confirm`监听`ack/nack`回调（你现在做的） | ❌不需要 |
| 想让 Spring 自动在发送失败时重试（连接断了等） | ✅需要（仅适用于连接类失败） |
| 自己实现手动重试逻辑（根据`nack`重发） | ❌不需要，优先使用你手动逻辑 |

#### 💡换句话说：

你**只使用**`ConfirmCallback`**来监听消息是否被 RabbitMQ 确认（ack/nack）**，就算是收到`nack`，也不会抛出异常 —— 只是**回调里返回了一个“不成功”的结果**。

所以：

---

### ✅不会抛异常，不触发 retry 配置

- `ConfirmCallback` 是消息 **发送后的回执机制** ，无论成功与否， **都不会导致** `RabbitTemplate.convertAndSend()` **抛出异常** ；
- `spring.rabbitmq.template.retry.*` 这套配置项，是为了解决以下情况：

- RabbitTemplate 发送消息时，遇到网络断开、RabbitMQ 挂了、连接超时等；
- 此时才会触发 retry 机制 **进行连接层的重试** ；

- 而你关注的 ack/nack 是 RabbitMQ **内部投递流程** 成功与否的结果，不属于连接问题，不触发 retry。

---

#### 🧪举例验证逻辑：

```plain
java


复制编辑
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) {
        System.out.println("消息发送失败，但不会抛异常，也不会自动 retry");
    }
});
```

你会发现：

- 消息如果路由失败、交换机不存在，回调会打印失败；
- 但代码仍然正常执行；
- **不会抛异常** 、 **不会触发 retry** ；
- 所以你必须手动处理是否要重发。

---

### ✅结论：

| 场景 | 是否触发异常 | 是否用到`template.retry.*` |
| --- | --- | --- |
| 消息 confirm 回调（ack/nack） | ❌不抛异常 | ❌不需要配置 |
| RabbitMQ 宕机 / 无法连接 | ✅抛异常 | ✅可以配置自动 retry |
