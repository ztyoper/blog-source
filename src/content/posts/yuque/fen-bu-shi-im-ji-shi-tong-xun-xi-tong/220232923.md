### **三、XSS漏洞介绍**

XSS（Cross-site scripting）漏洞是一种常见的Web安全漏洞，攻击者可以通过在网站中注入恶意代码来实现攻击。攻击者注入的代码会被其他用户浏览器执行，从而导致窃取用户敏感信息、篡改网页内容、甚至控制用户账号等风险。所以，在常见的Web系统中，我们需要在设计和研发系统时，避免出现XSS漏洞，造成不必要的损失。

XSS漏洞通常分为三种类型：反射型、存储型和DOM-based。

1. 反射型XSS漏洞：攻击者通过构造特定的URL `https://example.com/search?q=<script>stealCookie()</script>` 来触发，用户点击 -&gt; 自动跳转/登录 -&gt; 恶意脚本被执行（如远程发送 cookie、token 给攻击者）

> 当搜索 eggBig 时，如果没有搜索到，前端代码则会展示：未搜索到`<b>eggBig</b>`,如果搜索的 url 变为`eggBig<script>alert("哈哈")</script>`页面代码变成`<b>eggBig<script>alert("哈哈")</script></b>`，加载后则会执行 alert 脚本操作。
> **防范：**进行 html 转义：`<b>eggBig<script>alert("哈哈")</script></b>`修改为：`<b><script>alert("哈哈")</script></b>`
> 这样浏览器渲染时，就不会执行脚本了，而是展示文本内容：未搜索到`<b>eggBig<script>alert("哈哈")</script></b>`

2. 存储型XSS漏洞：攻击者将恶意脚本上传到服务器保存在数据库中，并在用户访问包含该脚本的页面时，恶意脚本被执行（如远程发送 cookie、token 给攻击者）。

> **防范：存储评论信息时**进行 html 转义：`<b>eggBig<script>alert("哈哈")</script></b>`修改为：`<b><script>alert("哈哈")</script></b>`这样浏览器渲染时，就不会执行脚本了，而是展示**文本内容**：未搜索到`<b>eggBig<script>alert("哈哈")</script></b>`

3. DOM-based XSS漏洞：攻击者 **不通过服务器返回脚本** ，而是利用浏览器端的 JavaScript 对 DOM 的操作，把恶意内容插入到页面中，从而触发执行。它 **完全发生在客户端** ，服务器端可能完全察觉不到。

> 网站的源码因为同时存在可以操作的属性和方法，导致网页文档结构被修改，这就是DOM型XSS。XSS发展到现在已经不再是单纯地跨站攻击了，我们不要被名字和概念迷惑，虽然还有其它类型，但总的来说就是用**各种方法注入并执行恶意脚本**。
> 这种攻击特别容易出现在：
> - `location.search` , `location.hash` , `document.referrer` , `window.name` 等来源未校验；
> - 使用 `innerHTML` 、 `document.write()` 、 `eval()` 、 `setTimeout(str)` 等危险方法。

对于XSS漏洞，一些常规的解决方案如下所示。

1. 输入验证和过滤：对用户输入的数据进行验证和过滤，确保输入数据符合预期格式，并剔除潜在的恶意脚本。

2. 输出编码：对输出到网页的数据进行适当的编码，以防止恶意脚本被执行。

3. 使用安全框架和库：使用具有内置安全机制的框架和库，例如使用Web应用程序防火墙（WAF）来检测和阻止XSS攻击。

4. 限制脚本执行权限：使用CSP（内容安全策略）来限制页面加载的资源来源，从而减少XSS攻击的成功率。

5. 定期更新和修复漏洞：及时更新和修复已知的安全漏洞，保持应用程序和服务器的安全性。

### **六、编码实现**

本节的编码实现比较简单，就是实现XSS规则的具体实现类XssRuleChainService。

源码详见：io.binghe.im.platform.common.risk.rule.service.impl.XssRuleChainService。

```java
@Component
public class XssRuleChainService extends BaseRuleChainService implements RuleChainService {
    private final Logger logger = LoggerFactory.getLogger(XssRuleChainService.class);
    ​
    @Value("${bh.im.rule.xssRule.enabled}")
    private Boolean xssRuleEnabled;
    ​
    @Value("${bh.im.rule.xssRule.order}")
    private Integer xssRuleOrder;
    ​
    @Override
    public HttpCode execute(HttpServletRequest request, Object handler) {
        //未开启XSS规则，直接通过校验
        if (BooleanUtil.isFalse(xssRuleEnabled)){
            return HttpCode.SUCCESS;
        }
        // 检查参数
        Map<String, String[]> paramMap = request.getParameterMap();
        for(String[] values:paramMap.values()){
            for(String value:values){
                if(XssUtils.checkXss(value)){
                    return HttpCode.XSS_PARAM_ERROR;
                }
            }
        }
        // 检查body
        String body = getBody(request);
        if(XssUtils.checkXss(body)){
            return HttpCode.XSS_PARAM_ERROR;
        }
        return HttpCode.SUCCESS;
    }
    ​
    @Override
    public int getOrder() {
        return xssRuleOrder == null ? RuleEnum.XSS.getCode() : xssRuleOrder;
    }
    ​
    @Override
    public String getServiceName() {
        return RuleEnum.XSS.getMesaage();
    }
    ​
    private String getBody(HttpServletRequest request){
        StringBuilder sb = new StringBuilder();
        try{
            BufferedReader reader = request.getReader();
            String line;
            while ((line = reader.readLine()) != null) {
                sb.append(line);
            }
        }catch (IOException e){
            logger.error("XssInterceptor.getBody|获取请求体异常:{}", e.getMessage());
        }
        return sb.toString();
    }
}
```

可以看到，XssRuleChainService类继承了BaseRuleChainService类，并实现了RuleChainService接口。在XssRuleChainService类中，通过@Value注解为成员变量xssRuleEnabled和xssRuleOrder注入了值，xssRuleEnabled表示是否开启XSS校验规则，xssRuleOrder表示XSS校验规则在整个拦截器规则链中的顺序。

在execute()方法中，首先会对xssRuleEnabled成员变量进行判断，如果值为false，说明不开启XSS校验规则，直接返回成功状态码。否则，表示开启XSS校验规则，对URL上拼接的参数和请求体中的参数进行XSS校验。整个流程还是比较简单的。
